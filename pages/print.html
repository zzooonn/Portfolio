BUAA OS — MIPS 마이크로커널 운영체제

2024.03 – 2024.07 BUAA OS Course OS Kernel Developer · 1인 개발
GXemul MIPS 시뮬레이터 위에서 커널 부팅 · 가상메모리 · CoW fork · 마이크로커널 FS를 7단계로 직접 구현 ✓ Lab 0–6 전 단계 완주

GXemul 환경에서 Lab0~Lab6의 7단계 커리큘럼을 따라 커널 부팅·메모리 관리·프로세스·시스템콜·IPC·파일시스템까지 OS의 핵심 구성요소를 단계적으로 직접 구현했습니다. 특히 TLB Fast Refill, Copy-on-Write 기반 fork(), 마이크로커널 파일시스템 구조를 구현하며 운영체제 핵심 메커니즘을 깊이 실습했습니다.

주요 개발 내용 (Lab 0 – Lab 6)
  • 커널 부팅 및 메모리 초기화 (Lab0–1): GXemul 부트스트랩 코드 작성, 물리 메모리 레이아웃 설정 및 커널 엔트리 포인트 초기화.
  • 가상 메모리 (Lab2): 2단계 페이지 테이블 기반 가상 주소 공간 설계, TLB Miss Fast Refill 핸들러를 어셈블리로 직접 작성해 TLB 관리 오버헤드 최소화.
  • 프로세스 스케줄링 (Lab3): PCB 설계, 라운드 로빈 스케줄러 구현, 컨텍스트 스위칭 시 레지스터 상태 저장·복원 로직 직접 작성.
  • Copy-on-Write fork() (Lab4): 페이지 공유 후 쓰기 시 예외 기반 실제 복사가 일어나는 COW 메커니즘 적용, 지연 평가(Lazy Evaluation)로 메모리 복사 비용 최적화.
  • Pipe IPC + 마이크로커널 FS (Lab5–6): 공유 페이지 기반 파이프 구현 및 독립된 FS 서버 프로세스와 IPC로 통신하는 마이크로커널 구조 구현.
Pipe IPC — pageref 판정 레이스 컨디션 해결
Kernel / IPC
상황

dup() · close() 실행 시, FD와 Pipe 페이지의 매핑·해제 순서에 따라 pageref 값이 일시적으로 의도와 다르게 관측되는 레이스 컨디션 발생.

대안 탐색

인터럽트 비활성화로 임계 구간 보호 검토 → 성능 저하·설계 원칙 위배로 제외. 매핑 순서 재배치(Reordering)로 불변식 유지 방안 선택.

해결

pageref(fd) ≤ pageref(pipe) 조건이 어떤 순간에도 깨지지 않도록 unmap · map 순서를 조정했습니다.

pipe.c — Atomic-like Mapping
// [Fix] FD를 먼저 해제하여
// pageref(fd) > pageref(pipe) 찰나의 순간 방지
void pipe_close(int fdnum) {
  syscall_mem_unmap(0, fd_to_va(fdnum));
  syscall_mem_unmap(0, pipe_to_va(fdnum));
}
알게된 점

선점형 스케줄링에서는 '완성된 결과'뿐만 아니라 '과정 중의 중간 상태'도 안전해야 함을 깨달았습니다. 불변식 보장을 코드 레벨에서 강제하는 습관을 만들었습니다.

  • 재귀 하향 파서(Parser): CompUnit 선행 탐색, LVal = Exp vs [Exp] 모호성 판별, 연산자 우선순위 기반 계층적 식(Expression) 파싱 구현.

Fault-Tolerant 파서 — 연쇄 파싱 에러 및 중복 오진 문제 해결
Compiler / Parser
상황

int a int b;처럼 세미콜론 누락 케이스를 처리하려고 에러 함수를 추가하면, 기존에 통과하던 정상 파싱까지 깨지는 문제 반복. parseErrorI/J/K가 mCurToken을 직접 소비하는 함수여서, 호출 순서가 조금만 바뀌어도 후속 구문이 엉뚱한 토큰에서 시작했습니다.

해결

에러 함수를 토큰 소비형 / look-ahead형 / 심볼 등록형으로 분류. 복구 로직은 현재 위치 저장 → 토큰 미리 확인 → 원위치 복귀로 정리. 누락 토큰은 직전 의미 단위(mLastNonT) 기준 기록.

Parser.cpp — Error Recovery
// parseErrorI/J/K 는 토큰 소비 함수
bool Parser::parseErrorI() {
  if (mCurToken.word != ";") {
    m_pErrorHandler->PushErrorList(
      'i', mLastNonT);  // 마지막 위치 기준
    return true;
  }
  AdvanceToNextToken();   // ← 소비
  return false;
}
알게된 점

문제 해결 시 재현 가능한 최소 입력을 만들고, 상태를 바꾸는 함수와 읽기만 하는 함수를 구분해야 한다는 점을 배웠습니다. 에러 처리는 예외 출력보다 파서의 현재 위치·문맥 보존 설계가 더 중요했습니다.

@RestControllerAdvice
public class ResponseResultHandler
    implements ResponseBodyAdvice<Object> {

  @Override
  public Object beforeBodyWrite(Object body,...) {
    if (body instanceof ResultWrapper)
      return body;
    return ResultWrapper.success(body);
  }
}
