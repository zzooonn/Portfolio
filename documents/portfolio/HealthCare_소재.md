# 모델을 만드는 일보다, 모델이 함부로 말하지 않게 만드는 일이 더 어려웠다

CareLink는 노인의 건강 기록과 심전도 분석을 돕기 위해 혼자 진행한 졸업논문 프로젝트다.

처음에는 목표가 단순했다.  
12유도 심전도 데이터를 학습시켜 정상과 이상 소견을 분류하고, 결과를 앱에서 볼 수 있게 만드는 것이었다.

그래서 처음에는 모델의 정확도에 가장 많은 관심을 뒀다.

어떤 구조가 더 높은 AUC를 만들 수 있는지,  
레이어를 얼마나 쌓아야 하는지,  
PyTorch 학습을 어떻게 빠르게 돌릴 수 있는지가 중요한 문제처럼 보였다.

프로젝트를 마친 지금은 생각이 달라졌다.

AI 기능에서 정말 어려운 일은 높은 수치 하나를 얻는 것이 아니었다.

**학습 데이터에서 잘 동작한 모델이 실제 입력에서도 같은 의미로 판단하게 만들고, 잘못된 입력에는 판단하지 않으며, 제한된 서버 자원에서도 지속해서 실행되게 만드는 일**이었다.

이 프로젝트는 내게 모델 하나를 학습시키는 경험보다, AI의 판단이 성립하는 조건 전체를 설계하는 경험으로 남았다.

---

## [더 큰 모델보다, 어떤 정보를 잃지 않을지가 먼저였다]

심전도는 12개의 유도에서 10초 동안 측정된 시계열 데이터다.

한 순간의 파형 모양도 중요하지만, 시간에 따른 변화와 유도 사이의 관계도 함께 봐야 한다.

처음에는 ResNet 계열처럼 더 큰 모델을 사용하는 것이 당연한 선택처럼 보였다.

하지만 CareLink는 연구용 실험으로 끝나는 프로젝트가 아니라, 결국 서버에 올려 앱에서 호출해야 하는 시스템이었다.

정확도가 조금 높더라도 모델이 너무 크면 추론 시간과 메모리 사용량이 늘어난다. 저사양 환경에서 운영하기 어려운 모델은, 논문 표의 수치가 좋아도 서비스에는 적합하지 않을 수 있었다.

그래서 CNN, CBAM, BiGRU를 결합한 구조를 선택했다.

CNN은 심전도 파형의 국소적인 변화와 형태를 읽고, CBAM은 12개 유도와 시간 구간 중 더 중요한 정보에 가중치를 둔다. 이후 BiGRU가 앞뒤 시간 흐름을 함께 보도록 했다.

여기에 정규화 이전의 진폭 정보를 별도 특징으로 계산해 결합했다.

정규화는 학습을 안정시키지만, 심전도에서 진폭 자체가 의미를 갖는 경우도 있다. 입력을 모두 같은 범위로 맞추는 과정에서 원래의 크기 차이까지 사라질 수 있었다.

그래서 나는 “정규화된 파형”만 모델에 넣는 대신, 유도별 peak-to-peak, 표준편차, RMS 같은 진폭 특징을 따로 보존했다.

이 선택은 단순히 모듈을 추가한 일이 아니었다.

**모델이 보기 편한 데이터로 바꾸는 과정에서, 판단에 필요한 정보까지 지우고 있지는 않은지 묻는 일이었다.**

그 결과 비교 대상인 ResNet1D보다 훨씬 작은 약 65만 개 파라미터로, 전체 성능은 비슷하게 유지하면서 HYP 범주에서는 더 나은 결과를 얻었다.

이때 처음으로 알게 됐다.

모델의 크기나 구조의 화려함보다 중요한 것은, **문제에서 무엇을 보존해야 하는지 먼저 정하는 일**이라는 것을.

## [평균 성능이 좋아졌다고, 더 나은 판단은 아니었다]

심전도 분류에는 정상, ST-T 변화, 심근경색, 전도 장애, 비대 같은 여러 범주가 함께 존재한다.

문제는 각 범주의 데이터 수가 같지 않다는 점이었다.

특히 데이터가 적은 범주는 전체 정확도에 미치는 영향이 작다. 모델이 드문 범주를 잘 놓쳐도 전체 점수는 높게 나올 수 있다.

처음에는 Macro AUC와 Macro F1이 높아지는 방향을 중심으로 봤다.

그러나 가중 샘플링을 제거한 실험에서 전체 Macro F1과 AUC가 오히려 좋아지는 결과를 확인했다. 숫자만 보면 더 나은 모델처럼 보였다.

그런데 세부 결과를 보면, 내가 특히 놓치고 싶지 않았던 HYP 범주의 성능은 떨어졌다.

전체 평균을 높이는 선택과, 적은 데이터의 중요한 범주를 더 잘 잡는 선택이 항상 같지는 않았다.

그래서 손실 함수와 샘플링 방식을 단순히 “성능 향상 기법”으로 보지 않게 됐다.

Asymmetric Loss, 양성 클래스 가중치, Weighted Random Sampler를 적용한 이유는 희소한 범주를 더 많이 보게 하기 위해서였다. 하지만 그것이 전체 지표를 항상 올려 주는 정답은 아니었다.

**평가 지표는 객관적인 점수판이 아니라, 어떤 실패를 더 크게 볼 것인지 정한 기준에 가까웠다.**

이후에는 “전체 점수가 가장 높은 모델”을 고르는 대신, 각 범주에서 어떤 오류가 늘고 줄었는지 함께 확인했다.

AI를 만든다는 것은 정답률을 최적화하는 일이 아니라,  
**누구의 어떤 실패를 줄이려 하는지 먼저 정하고 그 선택을 수치로 검증하는 일**이라는 점이 남았다.

## [모르는 입력을 0으로 바꾸는 순간, 모델은 거짓말을 시작했다]

서빙 단계에서도 비슷한 문제가 있었다.

초기 전처리 코드에서는 입력에 `NaN`이 들어오면 이를 0으로 치환하는 방식을 사용했다.

프로그램은 멈추지 않았다.  
모델도 결과를 반환했다.

하지만 어느 순간 이것이 잘못된 처리라는 생각이 들었다.

센서 오류나 전송 과정의 누락으로 생긴 `NaN`은 진폭이 0인 정상 신호가 아니다. 모르는 값을 0으로 바꾸면, 모델은 존재하지 않는 심전도 파형을 보고도 확률을 낸다.

사용자는 그 결과가 “입력이 깨져서 나온 값”인지, “모델이 실제 신호를 분석한 결과”인지 알 수 없다.

그래서 잘못된 값은 조용히 보정하지 않고 요청 자체를 거부하도록 바꿨다. 빈 배열, 유도 수가 다른 입력, 숫자가 아닌 값, `NaN`과 무한대, 잘못된 샘플링 주파수도 모두 검증 대상에 넣었다.

여기서 배운 것은 입력 검증이 단순한 예외 처리라는 사실이 아니었다.

**AI의 출력이 의미를 가지려면, 그 입력이 학습 때 모델이 보았던 데이터와 같은 전제를 만족해야 한다.**

학습 단계에서 정규화와 필터링을 정교하게 해도, 서빙 단계에서 그 전제가 무너지면 모델의 확률은 더 이상 같은 의미를 갖지 않는다.

“어떤 입력이 들어와도 결과를 보여 주는 모델”보다,  
**판단할 수 없는 입력에는 판단하지 않는 모델**이 더 신뢰할 수 있다는 기준이 생겼다.

## [AI를 분리한 이유는 기술 유행이 아니라, 서로 다른 생명주기 때문이었다]

CareLink에서는 심전도 모델을 Spring 서버 내부에 넣지 않고, PyTorch 기반 FastAPI 서버로 분리했다.

처음에는 단순히 역할을 나눈 구조라고 생각했다.

하지만 학습과 배포를 반복하면서, 이것은 코드 정리보다 더 근본적인 문제라는 것을 알게 됐다.

사용자 인증, 건강 기록, 보호자 연결 같은 기능은 일반적인 백엔드의 생명주기를 따른다. 반면 AI는 모델 가중치, Python·PyTorch 의존성, 전처리 규칙, 추론 자원처럼 전혀 다른 조건을 가진다.

모델을 교체하거나 롤백할 때 앱과 건강 기록 기능까지 함께 배포할 이유는 없다. 반대로 AI 서버의 메모리 문제가 사용자 인증 서버까지 멈추게 해서도 안 된다.

그래서 앱은 Spring 서버에만 요청하고, Spring이 인증과 요청 형식을 관리한 뒤 FastAPI 추론 서버에 전달하도록 구성했다.

이 구조를 통해 모델의 책임을 “확률을 계산하는 코드”에만 두지 않고,  
**학습·전처리·모델 가중치·추론 자원을 하나의 독립된 단위로 관리**하려 했다.

다만 다시 만든다면 이 경계는 더 엄격하게 만들고 싶다.

실험용 모델과 실제 서빙 모델의 전처리, 손실 함수, 임계값이 조금이라도 달라지면, 논문에서 검증한 성능과 서비스의 성능은 같은 결과라고 말할 수 없다.

다음에는 학습과 추론이 같은 전처리 모듈과 버전이 기록된 모델 아티팩트를 공유하도록 만들 것이다. 모델 파일만 배포하는 것이 아니라, **그 모델이 어떤 입력과 기준에서 유효한지까지 함께 배포**하고 싶다.

## [OOM은 모델의 문제가 아니라, 배포 경계의 문제였다]

가장 현실적인 문제는 저메모리 EC2 환경에서 만났다.

처음에는 서버 한 대에서 데이터베이스, Spring 서버, PyTorch AI 서버를 모두 실행하고 Docker 이미지까지 빌드하려 했다.

그때 메모리 사용량이 급격히 높아졌고, 서비스가 올라가기 전에 자원이 먼저 부족해질 수 있었다.

처음에는 모델을 더 작게 만들거나 코드 사용량을 줄이는 방향부터 생각했다.

하지만 원인은 모델 하나가 무거운 것만이 아니었다.

이미지를 빌드하는 순간의 자원 사용량, JVM과 PostgreSQL, PyTorch 모델 로딩이 한 서버에서 동시에 일어나는 구조가 문제였다.

그래서 해결 방향을 바꿨다.

이미지 빌드는 GitHub Actions에서 수행하고, EC2는 미리 빌드된 이미지를 내려받아 실행하도록 분리했다. 기본 경량 구성에서는 AI 컨테이너를 항상 실행하지 않고 필요할 때만 프로필로 올리도록 했다. 컨테이너별 메모리 제한과 swap도 추가했다.

여기서 메모리 제한은 OOM을 해결하는 만능 장치가 아니었다.

한 컨테이너의 폭주가 다른 서비스까지 무너뜨리는 것을 막는 경계에 가까웠다.

이 경험 이후 자원 문제를 “서버 사양이 부족하다”는 말로 끝내지 않게 됐다.

**빌드와 실행을 같은 환경에 두어도 되는지, 항상 켜져 있어야 하는 서비스가 무엇인지, 하나의 실패가 어디까지 번질 수 있는지를 먼저 나누는 일이 배포 설계의 시작**이라는 것을 배웠다.

다시 설계한다면 학습 초기에 정확도만 기록하지 않고, 모델 초기화 시간, 추론 지연, 컨테이너별 메모리 최고 사용량까지 함께 측정할 것이다. 운영 환경이 감당할 수 없는 모델은 좋은 모델 후보가 아니라는 기준을 처음부터 넣고 싶다.

## [AI 제품은 모델 하나가 아니라, 끊기지 않는 전제의 연결이었다]

CareLink를 시작할 때 나는 PyTorch로 심전도 분류 모델을 만들고, 앱에서 결과를 보여 주는 것이 목표라고 생각했다.

프로젝트를 마친 뒤 남은 것은 조금 다르다.

학습 데이터에서 보존해야 할 정보는 무엇인지,  
드문 범주의 실패를 얼마나 중요하게 볼 것인지,  
잘못된 입력을 어떤 방식으로 거부할 것인지,  
실험에서 얻은 결과가 실제 서빙에서도 같은 의미를 갖는지,  
그리고 제한된 자원 안에서 그 모델이 계속 실행될 수 있는지를 함께 설계해야 했다.

AI 제품은 모델 정확도와 API를 붙인 결과가 아니었다.

**데이터가 모델에 들어오는 순간부터, 모델의 출력이 사용자에게 전달되는 순간까지 지켜져야 하는 전제들의 연결**에 가까웠다.

CareLink에서 내가 배운 것은 더 복잡한 모델을 고르는 법이 아니다.

모델이 잘못된 근거로 말하지 않게 하고,  
전체 점수 뒤에 가려진 실패를 찾아내고,  
현실의 자원 제약 안에서도 그 판단이 계속 의미를 갖게 만드는 법이었다.
