# 틀린 코드를 끝까지 읽는 법

## [컴파일은 멈춰도 분석은 계속된다]

우리가 사용하는 컴파일러는 코드가 틀렸다고 곧바로 멈추지 않는다.

세미콜론 하나가 빠져 컴파일에 실패하더라도 몇 번째 줄에서 무엇이 잘못됐는지 알려준다. 오류가 여러 개라면 가능한 범위까지 뒤의 코드도 읽고 다른 문제를 함께 보여준다.

사용할 때는 너무 당연한 기능이었다. 직접 SysY 교육용 컴파일러를 만들기 전까지는 그랬다.

이 프로젝트에서 만들고자 한 것도 비슷했다. 잘못된 코드를 억지로 정상적인 프로그램으로 만드는 것이 아니라, 토큰이 일부 누락되어도 그 지점에서 분석 전체를 포기하지 않고 오류를 기록한 뒤 가능한 지점까지 파싱을 이어가는 것이었다.

처음에는 단순하게 생각했다.

필요한 토큰이 없다면 오류를 남기고 다음으로 넘어가면 된다고 생각했다.

문제는 그 **‘다음으로 넘어가는 방법’**이었다.

---

## [없는 문자를 찾아야 했다]

SysY 과제에서는 오류 유형마다 알파벳 코드가 붙었다. 그중 가장 오래 붙잡았던 것은 세 가지였다.

| 코드  | 누락된 토큰      | 예시            |
| --- | ----------- | ------------- |
| `i` | 세미콜론 `;`    | `a = 1`       |
| `j` | 오른쪽 소괄호 `)` | `if (a > b {` |
| `k` | 오른쪽 대괄호 `]` | `a[1 = 3;`    |

이 오류들은 다른 오류와 성격이 조금 달랐다.

예를 들어 다음 코드에서

```c
if (a & b)
```

`&`는 실제 입력 안에 존재한다. 파서는 눈앞에 있는 토큰을 보고 잘못됐다고 판단할 수 있다.

하지만 `i`, `j`, `k`는 그렇지 않았다.

```c
a = 1
b = 2;
```

여기에는 `;`라는 잘못된 토큰이 있는 것이 아니다.

`있어야 할 ;가 없다.`

이 차이가 중요했다.

현재 토큰이 틀린 것이 아니라 **현재 토큰 앞에 있어야 할 무언가가 사라진 상황**이었다. 따라서 지금 눈앞에 있는 토큰은 오히려 다음 문법이 정상적으로 사용해야 할 토큰일 수 있었다.

누락 오류를 처리하면서 가장 먼저 지켜야 했던 것은 의외로 단순했다.

**없는 토큰을 찾기 위해, 존재하는 정상 토큰을 잃으면 안 됐다.**

---

## [처음에는 오류 함수만 들여다봤다]

이 원칙 자체는 초기 단계에서도 어느 정도 알고 있었다.

오른쪽 소괄호를 검사하는 함수는 대략 이런 식이었다.

```cpp
void parseErrorPrintfJ() {
    Token currentToken = getCurrentToken();
    Token previousToken = getPreviousToken();

    if (currentToken.type == RPARENT) {
        outputToken(currentToken);
        advanceToken();
    }
    else {
        errors.push_back({ previousToken.lineNumber, 'j' });
    }
}
```

`)`가 있다면 정상적으로 소비하고, 없다면 오류만 기록한 채 현재 위치를 유지한다.

함수 자체의 원칙은 맞았다.

그래서 오류가 제대로 잡히지 않을 때마다 처음에는 이 함수 안을 들여다봤다. 줄 번호가 이상하면 `previousToken`을 쓸지 `currentToken`을 쓸지 바꿨다. `i`와 `j`는 이전 토큰을, `k`는 현재 토큰을 기준으로 삼는 식이었다.

각각에는 그럴듯한 이유가 있었다.

그런데 문제는 오류 함수 밖에 있었다.

---

## [한 토큰을 미리 읽은 대가]

5단계에서 `parseStmt()`는 대입문인지 표현식문인지 구분해야 했다.

```c
a = 1;      // 대입문
foo(a);     // 표현식문
```

앞으로 `=`가 나오는지를 알아야 했지만, 몇 번째 토큰에 등장할지는 미리 알 수 없었다.

그래서 처음에는 앞의 토큰을 직접 읽어보는 방식을 사용했다.

```cpp
int index = 0;
int isLVal = 0;
int tempLineNumber = mCurToken.lineNum;

while (true)
{
    if (mCurToken.word == ";") break;

    if (mCurToken.word == "=") {
        isLVal = 1;
        break;
    }

    if (tempLineNumber != mCurToken.lineNum) {
        parseErrorI();
    }

    index++;
    AdvanceToNextToken();
}

while (index) {
    MoveToPreviousToken();
    index--;
}
```

판단하기 위해 앞으로 이동하고, 몇 번 이동했는지를 `index`에 기록한 뒤 같은 횟수만큼 다시 되돌아오는 방식이었다.

처음에는 합리적으로 보였다.

현재 위치만으로 판단할 수 없다면 다음 토큰을 미리 읽어보면 된다. 그리고 읽은 만큼 다시 돌아오면 원래 상태도 유지할 수 있을 것 같았다.

문제는 파서가 그렇게 단순한 구조가 아니었다는 데 있었다.

오류 함수는 현재 토큰을 보존하고 있었지만, **그 함수를 호출하는 과정에서 이미 토큰 위치를 움직이고 있었다.**

`index`가 한 번만 어긋나도 이후의 파싱 위치가 달라졌다.

원래 다음 함수가 받아야 할 입력이

```text
b = 20;
```

이었다면,

실제로는

```text
= 20;
```

부터 받을 수 있었다.

`b` 하나가 사라졌을 뿐이지만 다음 파서는 식별자가 아니라 `=`부터 보게 된다. 그 순간부터 뒤의 정상 코드까지 문법적으로 이상한 입력처럼 보이기 시작한다.

더 큰 문제는 이미 P-code 생성까지 함께 진행되고 있었다는 것이다.

토큰 위치는 다시 돌려놓더라도, 전방 탐색 과정에서 만들어진 다른 상태까지 항상 함께 되돌아오는 것은 아니었다.

그때 알게 됐다.

각 파싱 함수 사이에는 코드에 명시하지 않은 약속이 있었다.

`parseExp()`는 표현식까지만 읽는다.

`parseStmt()`는 자기 문장까지만 읽는다.

그리고 **다음 문법의 첫 토큰은 다음 함수가 읽도록 남겨둔다.**

나는 누락 오류를 해결하려다가 그 약속을 깨뜨리고 있었다.

---

## [오류는 찾았는데 오류가 늘어났다]

반대쪽에서도 문제가 있었다.

```c
foo(a, b;
```

여기서 핵심 오류는 `)` 누락, 즉 `j` 하나다.

그런데 함수 호출 뒤에는 인자 개수 오류 `d`, 인자 타입 오류 `e` 같은 검사가 이어졌다.

당시의 흐름은 이랬다.

```text
) 없음
→ parseErrorJ()가 j 기록
→ 호출자로 복귀
→ 정상 함수 호출처럼 다음 처리
→ 인자 개수 검사
→ d 오류 추가
```

`parseErrorJ()`는 이미 “`)`가 없다”는 사실을 알고 있었다.

하지만 호출자는 그 사실을 알지 못한 채 정상적인 함수 호출이 끝난 것처럼 다음 검사를 수행했다.

여기서 질문이 바뀌었다.

처음에는

**“누락된 토큰을 어떻게 찾아서 어느 위치에 기록할까?”**

를 고민했다.

이제는

**“오류를 발견했다면 그 사실 때문에 다음 코드는 무엇을 다르게 해야 할까?”**

를 보기 시작했다.

오류를 알고 있다는 것과 시스템이 오류 상태를 공유하고 있다는 것은 다른 문제였다.

---

## [오류를 메시지에서 상태로]

가장 먼저 바꾼 것은 함수의 반환값이었다.

이전에는 오류를 기록하고 끝났다.

```cpp
void parseErrorPrintfJ();
```

그러면 호출자는 내부에서 무슨 일이 있었는지 알 방법이 없다.

그래서 반환값을 만들었다.

```cpp
bool Parser::parseErrorJ()
{
    if (mCurToken.word != ")") {
        m_pErrorHandler->PushErrorList('j', mLastNonT);
        return true;
    }
    else {
        AdvanceToNextToken();
    }

    return false;
}
```

변경 자체는 작았다.

`void`가 `bool`이 됐다.

하지만 오류의 의미가 달라졌다.

이전까지 오류는 나중에 사용자에게 보여주기 위한 **기록**이었다.

이제는 다음 코드의 행동을 결정하는 **상태**가 됐다.

---

## [신뢰할 수 없는 검사는 하지 않았다]

반환값을 만들자 호출부에서도 선택할 수 있게 됐다.

```cpp
if (!parseErrorJ()) {
    if (mFuncparse.back().expectedcnt != mFuncparse.back().paramcnt) {
        parseErrorD(mLastFuncLine);
    }
}
```

뜻은 단순하다.

`)`가 정상적으로 존재한다면 인자 개수를 검사한다.

하지만 `)`가 빠졌다면 `j` 오류만 기록하고 인자 개수 검사는 하지 않는다.

이전에는

```text
) 누락
→ 오류 기록
→ 정상 흐름 계속
→ 인자 개수 검사
→ 파생 오류 발생
```

했다면,

이후에는

```text
) 누락
→ 오류 기록
→ 오류 상태 전달
→ 현재 상태에서 신뢰하기 어려운 검사 생략
→ 정상 토큰 보존
→ 이후 파싱 계속
```

으로 바뀌었다.

여기서 생각 하나가 달라졌다.

처음에는 좋은 컴파일러라면 가능한 한 많은 오류를 찾아야 한다고 생각했다.

하지만 `)` 하나가 빠졌는데 오류가 열 개 나온다면, 정말 열 개를 발견한 것인지 다시 생각해야 했다.

아홉 개는 컴파일러가 첫 번째 오류를 제대로 통제하지 못해서 스스로 만들어낸 오류일 수도 있다.

사용자에게 필요한 것은 많은 빨간 줄이 아니다.

**원인을 고칠 수 있는 오류와, 그 이후에도 신뢰할 수 있는 분석 결과다.**

현재 전제가 무너졌다면 그 전제를 필요로 하는 검사를 하지 않는 쪽이 오히려 더 정확할 수 있었다.

---

## [줄 번호에도 기준이 필요했다]

누락 오류에서는 오류를 어느 줄에 표시할지도 별개의 문제였다.

예를 들어

```c
foo(a, b
;
```

처럼 작성돼 있다면 현재 토큰 `;`는 이미 다음 줄에 있다.

그 줄을 `)` 누락 위치라고 표시하면 실제 사용자가 수정해야 할 곳과 어긋난다.

초기에는 오류마다 기준이 달랐다.

`i`와 `j`는 `previousToken`을 사용했고, `k`는 `currentToken`을 사용했다.

이후에는 마지막으로 정상적으로 확인한 비단말 위치인 `mLastNonT`를 기준으로 삼았다.

```cpp
m_pErrorHandler->PushErrorList('j', mLastNonT);
```

오류마다 위치를 따로 추측하는 대신 하나의 기준을 갖게 됐다.

---

## [같은 이름도 같은 대상은 아니었다]

토큰 소비와 별개로 끝까지 어려웠던 문제 중 하나는 이름이었다.

```c
int x;

int foo(int x) {
    return x + 1;
}

int main() {
    int x;
    x = foo(x);
}
```

소스 코드에는 같은 `x`가 반복해서 등장한다.

하지만 각각은 전역 변수, 매개변수, 지역 변수처럼 다른 대상이다.

컴파일러가 보는 것은 모두 같은 문자열 `"x"`였다.

이름만으로는 구분할 수 없었다.

그래서 심볼에 두 가지 좌표를 붙였다.

```cpp
struct SymbolTable {
    std::string name;
    int type = -1;
    int kind = -1;
    int scope;
};
```

`kind`는 **무엇인가**를 나타내고,

`scope`는 **어디에 속해 있는가**를 나타냈다.

같은 이름이라도 두 정보가 달라지면 서로 다른 심볼이 된다.

---

## [안쪽에서 바깥으로]

등록만으로는 충분하지 않았다.

실제 코드에서 `x`를 만났을 때 여러 `x` 가운데 어느 것을 가리키는지 결정해야 했다.

그래서 현재 가장 안쪽 스코프부터 바깥으로 올라가며 탐색했다.

```cpp
std::stack<int> tempScopeStack = mScopeStack;

while (!tempScopeStack.empty()) {
    int currentScope = tempScopeStack.top();
    tempScopeStack.pop();

    SymbolTable* symbol =
        m_pSymbolTableMgr->findSymbol(name, currentScope);

    if (symbol != nullptr) {
        // 찾으면 사용
        break;
    }
}
```

`main()` 내부에 지역 `x`가 있다면 그것이 먼저 발견되고, 전역 `x`는 자연스럽게 가려진다.

shadowing을 별도의 예외 규칙으로 만들기보다 **탐색 순서 자체가 규칙**이 됐다.

## [재귀는 이름을 언제 등록하느냐의 문제였다]

재귀 함수에서는 순서가 중요했다.

```c
int fact(int n) {
    if (n <= 1) return 1;
    return n * fact(n - 1);
}
```

함수 몸통을 읽다가 `fact`를 다시 만났는데, 아직 심볼 테이블에 `fact`가 등록되지 않았다면 미정의 오류가 발생한다.

그래서 함수 이름을 몸통보다 먼저 등록했다.

```text
함수 이름 등록
→ 함수 내부 스코프 생성
→ 매개변수 등록
→ 함수 몸통 파싱
```

재귀 자체를 따로 특별하게 처리한 것이 아니라, **이름이 필요한 시점보다 먼저 존재하게 만드는 것**이 핵심이었다.

## [스코프를 숫자로 기억한 대가]

원리는 정리됐지만 구현에서는 또 다른 문제가 생겼다.

심볼 테이블은 스코프 트리가 아니라 하나의 평평한 `vector`였고, 소속은 `scope` 번호로 구분했다.

그래서 세 상태를 계속 맞춰야 했다.

`mGlobalSymbolScope`는 새 번호를 만들고,

`mCurScope`는 현재 위치를 기억하고,

`mScopeStack`은 이전 위치로 돌아가기 위해 사용했다.

함수 안에 블록이 있고 그 안에 다시 블록이 있기 때문에 `++`, `--`, `push`, `pop`의 짝 하나만 틀어져도 뒤의 모든 스코프가 달라질 수 있었다.

비슷한 상태 변수도 많았다.

전역인지, 함수 안인지, 반환값이 필요한지, `return`을 이미 만났는지, 반복문 안인지 같은 문맥을 파서가 직접 기억해야 했다.

문제는 이러한 상태들이 서로 떨어진 여러 위치에서 바뀐다는 것이었다.

어떤 함수에 들어갈 때 값을 바꾸고, 빠져나올 때 다시 되돌려야 했다.

중간 오류 때문에 복원이 한 번 빠지면 증상은 전혀 다른 함수에서 나타났다.

버그가 보이는 위치와 원인이 생긴 위치가 수백 줄 떨어질 수도 있었다.

결국 스코프 번호와 여러 상태 변수의 문제는 같은 곳을 가리켰다.

**‘현재 내가 어디에 있고 어떤 문맥인가’라는 하나의 사실을 여러 변수에 복제해 놓고 사람이 직접 동기화하고 있었다.**

---

## [문제가 있는 곳을 찾을 수 있게 만들었다]

여기까지 수정하고도 코드 구조 자체의 문제가 남아 있었다.

Lexer, Parser, ErrorHandler, SymbolTableManager, Interpreter, P-code 관련 로직이 하나의 큰 파일에 함께 들어가 있었다.

오류 하나를 고치기 위해 전체 코드를 봐야 했다.

토큰 위치가 잘못된 것인지,

심볼 탐색이 틀린 것인지,

오류 출력이 문제인지,

P-code 실행이 문제인지,

증상만 보고서는 알기 어려웠다.

그래서 최종적으로 책임을 나눴다.

`Lexer`는 토큰을 만들고,

`Parser`는 구문·의미 분석과 P-code 생성을 맡고,

`ErrorHandler`는 오류의 저장과 정렬·출력을 맡고,

`SymbolTableManager`는 심볼을 관리하고,

`Interpreter`는 P-code를 실행하도록 했다.

완전한 계층 분리는 아니었다.

`Parser`에는 여전히 많은 책임과 상태가 남아 있었다.

그래도 차이는 있었다.

문제가 생겼을 때 **어디를 먼저 봐야 하는지는 알 수 있게 됐다.**

---

## [CMake는 답이 아니라 결과였다]

파일을 나누자 다음 문제가 생겼다.

단일 `.cpp` 하나일 때는 그냥 그 파일을 컴파일하면 됐다.

하지만 여러 `.cpp`로 나누고 나니 어떤 파일들을 하나의 프로그램으로 묶을 것인지 관리해야 했다.

그래서 CMake를 사용했다.

```cmake
set(SOURCE_FILES
    ComplierSysY.cpp
    ErrorHandler.cpp
    Interpreter.cpp
    Lexer.cpp
    Parser.cpp
    SymbolTableManager.cpp)

add_executable(Compiler ${SOURCE_FILES})
```

여기서 중요한 것은 CMake 자체가 아니었다.

빌드 도구를 도입해서 코드 구조가 좋아진 것이 아니라,

**책임을 먼저 나눴고, 그 구조를 유지하기 위한 빌드 방식이 필요해진 것**이었다.

순서는 이쪽이었다.

## [복구는 코드를 고쳐 쓰는 일이 아니었다]

처음에는 ‘오류 복구’라는 말을 다르게 이해했다.

`)`가 없다면 컴파일러가 그것을 보충해 어떻게든 정상 코드처럼 만들어주는 것이 복구라고 생각하기 쉽다.

하지만 프로젝트에서 필요한 것은 그런 일이 아니었다.

코드는 여전히 잘못돼 있다.

컴파일은 실패해도 된다.

중요한 것은 **하나의 오류 때문에 그 뒤의 정상 코드까지 잃지 않는 것**이었다.

누락된 `)`는 누락됐다고 기록한다.

대신 다음에 있는 `;`까지 잘못된 토큰으로 소비하지 않는다.

그리고 다시 신뢰할 수 있는 문법 경계를 찾으면 거기서부터 분석을 이어간다.

결국 오류 복구는 오류를 없애는 기술이라기보다,

**오류의 영향이 어디까지 번지는 것을 허용할지 정하는 기술**에 가까웠다.

---

## [예외 처리에서 규칙으로]

처음에는 테스트가 깨질 때마다 해당 위치에 조건을 추가했다.

현재 토큰을 보고,

앞으로 한 칸 가보고,

필요하면 `index`만큼 되돌아왔다.

각 조건에는 나름의 이유가 있었다.

그래서 당시에는 하드코딩이라고 생각하지 않았다.

하지만 시간이 지나면서 다른 모습이 보였다.

특정 입력에서 맞도록 만든 조건이 다른 입력에서는 파서가 지켜야 할 규칙을 깨뜨리고 있었다.

그 뒤에는 개별 케이스보다 먼저 세 가지 기준을 보게 됐다.

> 각 파싱 함수는 자신이 담당하는 문법 범위까지만 토큰을 소비한다.
> 누락 토큰을 찾기 위해 정상 토큰을 함부로 소비하지 않는다.
> 오류는 기록에서 끝나지 않고 이후 어떤 처리를 신뢰할 수 있는지를 결정해야 한다.

이 기준이 생기자 테스트 하나를 통과시키는 것과 구조적으로 맞는 코드를 만드는 것을 구분할 수 있게 됐다.

여기서 얻은 교훈은 단순히 **‘하드코딩은 나쁘다’**가 아니었다.

임시 조건은 문제를 재현하거나 가설을 시험할 때 빠른 방법일 수 있다.

문제는 임시 처방이 잘 작동했다는 이유만으로 그것을 시스템의 규칙이라고 생각하는 순간이다.

**몇 개의 입력을 통과했다는 사실보다, 다른 입력에서도 반드시 지켜져야 할 조건을 설명할 수 있는지가 더 중요했다.**

## [오래 붙잡는 것과 끝까지 푸는 것은 달랐다]

이전에는 문제를 포기하지 않는다는 말을 단순하게 생각했다.

안 되면 더 오래 보고,

테스트를 더 돌리고,

조건을 하나씩 바꾸는 것이 끈기라고 생각했다.

실제로 처음에는 그렇게 했다.

한 테스트가 깨지면 토큰을 움직이는 방법을 바꾸고, 다른 테스트가 깨지면 다시 조건을 붙였다.

문제를 포기하지 않고 있었지만, 다른 의미에서는 **처음 세운 문제 정의를 포기하지 못하고 있었다.**

전환점은 코드를 더 많이 수정했을 때가 아니었다.

**“내가 지금 고치고 있는 것이 정말 원인인가?”**

를 다시 물었을 때였다.

처음에는 누락 토큰을 찾는 것이 문제라고 생각했다.

그다음에는 토큰 위치를 정확히 복원하는 것이 문제라고 생각했다.

결국 더 중요한 것은 **오류를 발견한 함수와 이후 처리를 담당하는 함수가 어떤 상태와 책임을 공유하는가**였다.

같은 문제를 오래 붙잡는 것과 문제를 끝까지 해결하는 것은 같지 않았다.

이 프로젝트에서 배운 끈기는 같은 답을 오래 밀어붙이는 태도보다,

**답이 계속 틀린다면 질문부터 다시 만드는 태도**에 가까웠다.

---

## [다시 만든다면 언어보다 구조부터 정하겠다]

프로젝트를 하면서 한동안 이런 생각도 했다.

“C++이라서 이렇게 복잡한 걸까. Java로 만들었다면 훨씬 깔끔했을까.”

지금은 절반만 맞는 생각이었다고 본다.

나는 `Parser`, `Lexer`, `Interpreter`라는 클래스를 사용했지만, 내부 구조는 상당히 절차적이었다.

`Parser` 하나가 많은 상태를 들고 있었고 여러 함수가 그 값을 직접 바꿨다.

클래스를 만들었다고 해서 상태의 책임까지 자동으로 분리되는 것은 아니었다.

다시 만든다면 스코프부터 객체로 만들고 싶다.

현재 구조에서는 스코프 번호 발급기, 현재 번호, 복귀용 스택을 각각 관리했다.

`Scope`가 자기 심볼과 부모 스코프를 직접 가졌다면 번호 세 개를 맞춰야 할 이유 자체가 줄어든다.

오류 상태 역시 `parseErrorJ()`만 `bool`이고 다른 함수는 다른 규칙을 갖는 대신, 처음부터 파싱 결과를 표현하는 공통 반환 타입을 정하는 편이 낫다.

그리고 가장 큰 변화는 AST를 먼저 만드는 것이다.

토큰을 한 번 읽으면서 구문 분석, 의미 검사, P-code 생성까지 함께 처리했기 때문에 현재 위치와 문맥을 많은 플래그로 들고 다녀야 했다.

트리를 먼저 만든 뒤 의미 분석과 코드 생성을 별도 단계로 수행했다면, 지금 어느 노드에 있는지가 문맥을 대신할 수 있다.

중요한 것은 이런 구조가 Java만의 장점은 아니라는 것이다.

C++에서도 모두 구현할 수 있다.

오히려 어떤 상태의 진입과 복원이 반드시 짝을 이뤄야 한다면 RAII 같은 C++의 기능을 사용할 수도 있었다.

결국 문제는 언어가 아니었다.

**규칙을 코드 구조가 강제하도록 만들지 않고, 내가 기억해서 지키려고 했던 것**에 가까웠다.

그래서 다시 만든다면 언어부터 고르지 않을 것 같다.

먼저 상태의 소유자가 누구인지,

오류를 어떻게 전달할 것인지,

파싱 단계를 어떻게 나눌 것인지,

진입과 복원을 누가 보장할 것인지를 정한 뒤 언어를 고를 것이다.

## [틀린 뒤의 행동을 설계하는 일]

SysY를 시작할 때 만들고 싶었던 것은 **어디가 틀렸는지 알려주는 컴파일러**였다.

직접 만들고 나서 더 오래 남은 질문은 그다음이었다.

**틀렸다는 사실을 알게 된 이후, 시스템은 어떻게 행동해야 하는가.**

모든 오류를 없앨 수는 없다.

사용자는 괄호를 빠뜨리고, 잘못된 입력은 들어온다.

중요한 것은 하나의 오류가 발생했을 때 나머지 정상 상태까지 함께 잃지 않는 것이다.

어디까지의 상태를 믿을 것인지,

어떤 검사는 더 이상 의미가 없는지,

어떤 입력은 보존해야 하는지,

그리고 어디에서 정상 흐름을 다시 시작할 것인지를 정해야 한다.

컴파일러에서는 그 대상이 토큰과 파싱 상태였다.

내가 SysY에서 얻은 것은 오류 없는 프로그램을 만드는 방법이 아니었다.

**눈앞의 오류를 통과시키기 위해 조건을 하나씩 추가하는 데서 벗어나, 오류가 생겨도 나머지 정상 상태를 지키기 위해 시스템 전체가 따라야 할 규칙을 찾는 법이었다.**

그 점이 이 프로젝트에서 가장 크게 바뀐 부분이었다.
