# 프로그램이 멈추지 않게 하는 것은 정상 코드만이 아니었다

## [운영체제는 알고 있었지만, 끝났다는 말은 몰랐다]

운영체제는 이미 수업에서 배운 적이 있었다.

프로세스가 무엇인지, 가상 메모리가 왜 필요한지, 시스템 콜이 사용자 프로그램과 커널 사이의 경계를 만든다는 것도 알고 있었다. 페이지 테이블을 따라 주소를 변환하고, 프로세스의 상태 전이를 설명하는 일도 낯설지 않았다.

그래서 MIPS R3000 기반 교육용 운영체제를 구현하기 시작할 때도, 필요한 기능을 순서대로 만들면 된다고 생각했다.

```text
부팅
→ 메모리 관리
→ 프로세스 관리
→ 예외와 시스템 콜
→ fork와 IPC
→ 파일 시스템
→ shell
```

각 Lab의 테스트를 통과할 때마다 하나의 기능을 끝냈다고 생각했다.

그런데 레포지토리의 README에는 마지막 Lab 코드를 기준으로 이전 Lab의 버그까지 다시 확인하라는 설명이 있었다. 뒤로 갈수록 앞에서 구현한 코드의 전제가 깨지는 일이 생긴다는 뜻이었다.

처음에는 이상하게 느껴졌다.

앞의 테스트를 통과한 코드가 왜 뒤에 가서 다시 문제가 될까.

마지막 Lab에서 pipe와 shell을 구현하면서 그 이유를 알게 됐다.

**코드가 정상적으로 끝난다는 사실과, 시스템이 올바르게 동작한다는 사실은 같지 않았다.**

---

## [비어 있다는 것과 끝났다는 것은 달랐다]

shell에서 다음 명령을 실행한다고 해보자.

```sh
cat a.txt | grep hello
```

사용자에게는 `cat`의 출력이 `grep`의 입력으로 넘어가는 한 줄의 명령이다.

하지만 pipe 입장에서는 두 가지 상태를 구분해야 한다.

```text
지금 버퍼가 비어 있다.
더 이상 데이터를 쓸 writer가 없다.
```

처음에는 둘의 차이를 크게 생각하지 않았다.

버퍼가 비어 있으면 `read()`는 읽을 데이터가 없으니 반환하면 된다고 여겼다.

하지만 빈 버퍼는 끝난 버퍼가 아니다.

writer가 아직 살아 있다면, 지금은 데이터가 없더라도 다음 스케줄 차례에 새 데이터를 쓸 수 있다. 이때 reader가 `0`을 반환하면 호출자는 EOF, 즉 “더 이상 읽을 데이터가 없다”고 해석한다.

실제 초기 pipe 코드도 버퍼가 비어 있을 때 바로 반환하는 흐름에 가까웠다. 이후 코드는 버퍼가 비어 있으면 반복해서 닫힘 여부를 확인하고, writer가 살아 있으면 `yield()`로 CPU를 양보한 뒤 다시 기다리도록 바뀌었다.

```text
버퍼가 비어 있음
→ writer가 닫혔는지 확인
→ 닫히지 않았다면 yield
→ 다시 읽기 시도
```

코드 변화는 작았다.

하지만 이 수정은 내게 “현재 데이터가 없다”와 “앞으로도 데이터가 오지 않는다”가 서로 다른 상태라는 사실을 남겼다.

처음에는 pipe를 단순한 버퍼로 보았다.

그 뒤에는 pipe를 **시간에 따라 의미가 달라지는 약속**으로 보게 됐다.

## [닫혔다는 판단은 참조 횟수 하나로 끝나지 않았다]

이 OS의 pipe는 커널 안에 별도 pipe 객체를 두지 않는다.

유저 공간에서 Pipe 데이터 페이지를 만들고, read fd와 write fd가 그 페이지를 공유한다. 실제 read와 write도 유저 라이브러리에서 수행한다.

그래서 반대편이 닫혔는지 판단할 때 커널에게 writer 수를 묻지 않는다. 대신 페이지 참조 횟수를 비교한다.

```text
Fd 페이지의 참조 수          → pageref(fd)
Pipe 데이터 페이지의 참조 수 → pageref(pipe)
```

반대편이 살아 있는 동안에는 Pipe 데이터 페이지의 참조 수가 더 크다.

```text
pageref(fd) < pageref(pipe)
```

반대편이 모두 닫히면 두 값이 같아지고, 그때 EOF로 판단한다.

처음에는 이 규칙이 충분해 보였다.

참조 횟수의 최종값만 맞으면 되는 것 아닌가 생각했다.

하지만 `dup()`과 `close()`는 하나의 논리적 작업이면서도 실제로는 두 단계로 나뉜다. Fd 페이지와 Pipe 데이터 페이지를 각각 매핑하거나 해제해야 하기 때문이다.

```text
첫 번째 페이지 변경
        ↓
        ← timer interrupt 가능
        ↓
두 번째 페이지 변경
```

두 시스템 콜 사이에 다른 프로세스가 실행되면, 참조 횟수는 작업 전도 후도 아닌 중간 상태가 된다.

## [마지막 값은 맞았지만, 중간의 값이 거짓말을 했다]

`testpiperace.c`는 이 문제를 의도적으로 재현한다.

부모 프로세스는 같은 read fd를 계속 `dup()`하고 닫는다. 자식 프로세스는 그 사이에 pipe가 닫혔는지 반복해서 확인한다. Pipe 버퍼의 크기도 32바이트로 작게 설정되어 있어 실행 순서에 따른 문제가 더 잘 드러난다.

잘못된 순서의 `close()`를 예로 들면 다음과 같다.

```text
시작: fd_ref = 3, pipe_ref = 4

Pipe 데이터 페이지 해제
→ fd_ref = 3, pipe_ref = 3

Fd 페이지 해제
→ fd_ref = 2, pipe_ref = 3
```

첫 번째 단계에서 writer는 여전히 살아 있다.

그런데 다른 프로세스가 바로 그 순간 `fd_ref == pipe_ref`를 읽으면 pipe가 닫혔다고 판단한다. 실제로는 writer가 살아 있는데 reader는 EOF를 반환하고, 파이프라인은 예상보다 일찍 끊긴다.

최종 상태는 맞다.

하지만 시스템은 최종 상태에 도착하기 전에 이미 틀린 결론을 냈다.

이 문제를 보면서 처음에는 “인터럽트가 하필 그 짧은 순간에 들어오는 경우”라고 생각했다.

그러나 운영체제에서 인터럽트와 스케줄 전환은 특별한 예외가 아니다. 시스템이 당연히 받아들여야 하는 실행 순서다.

그때부터 테스트를 보는 기준이 달라졌다.

정상 입력에서 원하는 출력이 나온다는 것은 내가 예상한 순서에서는 동작한다는 뜻일 뿐이었다.

**다른 프로세스가 내 코드의 중간 상태를 볼 수 있다면, 그 중간 상태도 이미 내가 책임져야 할 시스템의 일부였다.**

## [처음에는 mutex를 떠올렸다]

동시성 문제를 만나자 가장 먼저 떠오른 것은 lock이었다.

Fd 페이지와 Pipe 데이터 페이지를 바꾸는 동안 mutex를 잡고 다른 프로세스가 중간 상태를 읽지 못하게 하면 될 것 같았다.

실제 시스템에서 mutex와 spinlock은 중요한 도구다. 여러 실행 주체가 같은 상태를 바꾸려 할 때, 한쪽만 임계 구역에 들어가게 만들어 공유 자원을 보호한다.

하지만 이 pipe는 유저 공간 공유 페이지에 구현되어 있었다. 이 실습의 user-level pipe 경로에는 공용 mutex나 하드웨어 원자 연산이 제공되지 않았다.

그렇다고 단순히 “락이 없어서 다른 방법을 썼다”가 핵심은 아니었다.

다시 살펴보니 내가 정말 막고 싶은 것은 다른 프로세스의 모든 접근이 아니었다.

```text
writer가 살아 있는데도
fd_ref == pipe_ref가 관찰되는 상황
```

그 한 가지를 막고 싶었다.

lock을 추가하는 방식도 가능했을 것이다. 다만 그러면 lock의 소유권은 누가 갖는지, lock을 잡은 프로세스가 종료되면 누가 복구하는지, 유저 공간의 공유 페이지에서 lock의 수명을 어떻게 관리할지 같은 새로운 문제가 생긴다.

이 경험을 통해 mutex는 동시성 문제의 정답이 아니라, **어떤 상태를 어떤 방식으로 보호할지 결정한 뒤 선택하는 도구**라는 점을 배웠다.

---

## [락을 넣는 대신, 상태의 방향을 바꿨다]

실제 수정은 중간 상태를 숨기는 방식이 아니었다.

중간 상태가 위험한 의미를 갖지 않도록 만드는 방식이었다.

`dup()`에서는 Pipe 데이터 페이지를 먼저 매핑하고 Fd 페이지를 나중에 매핑하도록 순서를 바꿨다.

```text
pipe_ref를 먼저 증가
→ fd_ref를 나중에 증가
```

`close()`에서는 반대로 Fd 페이지를 먼저 해제하고 Pipe 데이터 페이지를 나중에 해제하도록 수정했다.

```text
fd_ref를 먼저 감소
→ pipe_ref를 나중에 감소
```

그러면 반대편이 살아 있는 동안 중간 상태에서도 다음 관계가 유지된다.

```text
fd_ref < pipe_ref
```

다른 프로세스가 상태를 보더라도 거짓 EOF라는 결론에 도달하지 못한다.

이 부분이 프로젝트에서 가장 오래 남았다.

이전에는 동시성 제어를 “아무도 보지 못하게 막는 일”이라고 생각했다.

하지만 여기서는 다른 프로세스가 상태를 보는 것 자체가 문제가 아니었다.

문제는 그 상태가 잘못 해석될 수 있다는 점이었다.

그래서 해결도 접근 차단이 아니라 상태 전이의 순서를 바꾸는 일이 됐다.

이후에는 동시성 문제를 만날 때 먼저 이렇게 묻게 됐다.

> 다른 실행을 반드시 막아야 하는가.  
> 아니면 중간 상태가 노출되어도 시스템의 약속을 깨지 않게 만들 수 있는가.

## [두 개의 값이 맞아도, 같은 시간을 말하는 것은 아니었다]

연산 순서를 바꾼 뒤에도 한 가지 문제가 남았다.

닫힘 여부를 판단하려면 두 값을 읽어야 한다.

```c
fd_ref = pageref(fd);
pipe_ref = pageref(pipe);
```

각 값은 정확할 수 있다.

하지만 첫 번째 값을 읽은 뒤 프로세스가 교체되면, 두 번째 값은 다른 시점의 값이 된다. 서로 다른 시간의 값 두 개를 하나의 상태처럼 비교하면 판단은 다시 틀릴 수 있다.

그래서 다음 수정에서는 `env_runs`가 추가됐다.

```c
do {
    runs = env->env_runs;
    fd_ref = pageref(fd);
    pipe_ref = pageref(pipe);
} while (runs != env->env_runs);
```

`env_runs`는 프로세스가 CPU를 할당받아 실행된 횟수다. 환경 생성 시 0으로 초기화되고, 스케줄러가 해당 프로세스를 다시 실행할 때마다 증가한다.

두 참조 수를 읽는 사이에 스케줄 전환이 있었다면 `env_runs` 값이 바뀐다. 그때는 두 값을 다시 읽는다.

이 코드는 두 값을 하드웨어 수준에서 원자적으로 읽게 만드는 것은 아니다. 이 교육용 OS의 단일 CPU 스케줄링 환경에서, 두 값이 같은 실행 구간에서 읽혔는지를 확인하는 장치다.

이 수정은 내게 또 다른 질문을 남겼다.

> 값 하나하나가 맞는 것과, 그 값들이 같은 상황을 설명하는 것은 같은가.

로그 두 개, 상태 변수 두 개, 성능 지표 두 개를 함께 볼 때도 마찬가지다. 각각의 값이 틀리지 않았더라도, 서로 다른 시점의 정보를 하나의 원인처럼 연결하면 판단은 틀릴 수 있다.

## [ACID를 떠올렸지만, 더 중요한 것은 불변식이었다]

이 문제를 보며 데이터베이스의 ACID도 떠올렸다.

물론 pipe는 데이터베이스 트랜잭션이 아니다. 메모리 기반 구조이므로 영속성까지 포함한 ACID를 그대로 적용할 수는 없다.

그럼에도 세 가지 관점은 도움이 됐다.

```text
Atomicity:
dup과 close는 하나의 논리적 작업이지만 여러 단계로 나뉜다.

Consistency:
반대편이 살아 있는 동안 fd_ref < pipe_ref가 유지되어야 한다.

Isolation:
다른 프로세스가 중간 상태를 보더라도 거짓 EOF를 판단하지 않아야 한다.
```

처음에는 이 문제를 “원자성이 부족해서 생긴 문제”라고만 생각했다.

그러나 모든 연산을 완전히 쪼개지지 않게 만들 수는 없다. 이 pipe도 `dup()`과 `close()`를 하나의 하드웨어 명령으로 바꾼 것은 아니다.

대신 쪼개진 각 단계가 시스템의 규칙을 깨지 않도록 만들었다.

그래서 이 경험에서 더 오래 남은 것은 ACID라는 용어 자체가 아니었다.

**모든 상태를 숨길 수 없다면, 노출되는 상태가 어떤 의미를 가져도 되는지 먼저 정해야 한다는 사실**이었다.

## [오류를 처리하는 코드도 정상 상태를 전제로 하면 안 됐다]

pipe에서 중간 상태를 보게 됐다면, Copy-On-Write에서는 복구 코드가 서 있는 기반을 보게 됐다.

`fork()`는 부모와 자식의 메모리를 즉시 모두 복사하지 않는다. 처음에는 같은 페이지를 공유하고, 쓰기가 발생했을 때만 새 페이지를 복사한다.

```text
페이지 공유
→ 쓰기 시도
→ TLB Mod 예외
→ page fault handler 실행
→ 새 페이지 복사
→ 쓰기 가능하도록 재매핑
```

그런데 page fault handler도 함수이므로 스택을 사용한다.

일반 유저 스택이 COW 페이지라면, 오류를 고치기 위해 실행된 handler가 스택에 값을 쓰는 순간 다시 같은 오류를 만들 수 있다.

```text
COW 스택에 쓰기
→ TLB Mod 예외
→ handler 실행
→ handler가 같은 COW 스택에 쓰기
→ 다시 TLB Mod 예외
```

그래서 이 OS는 일반 스택과 분리된 `UXSTACK`에 예외용 페이지를 할당하고, page fault handler가 그 위에서 실행되도록 한다.

처음에는 예외 스택을 COW 구현의 세부 사항으로 보았다.

하지만 다시 읽으며 남은 것은 다음 질문이었다.

> 시스템이 고장 났을 때, 그 고장을 처리하는 코드는 무엇을 믿고 실행되는가.

정상 코드는 정상 메모리와 정상 제어 흐름을 전제로 동작한다.

복구 코드는 이미 그 전제가 깨진 뒤에 실행된다.

따라서 복구 코드는 자신이 처리하려는 오류와 분리된, 별도로 보장된 기반 위에 있어야 했다.

## [다시 만든다면 pipe부터 만들지 않고, 약속부터 적겠다]

프로젝트 초반에는 기능 목록을 먼저 봤다.

메모리를 만들고, 프로세스를 만들고, 시스템 콜을 만들고, pipe를 만들면 된다고 생각했다.

지금 다시 만든다면 pipe의 read와 write 함수부터 작성하지 않을 것 같다.

먼저 pipe가 보장해야 하는 약속을 적을 것이다.

```text
버퍼가 비었다는 것은 무엇을 의미하는가.
EOF는 어떤 상태에서만 반환되어야 하는가.
reader와 writer가 여러 개여도 현재 참조 수 규칙은 유지되는가.
dup과 close의 중간 상태는 다른 프로세스에 어떻게 보이는가.
어떤 상태는 lock으로 보호해야 하고, 어떤 상태는 순서만으로 안전하게 만들 수 있는가.
```

그 뒤에야 구현 방식을 정할 것이다.

명시적인 reader·writer 수를 가진 pipe 객체를 둘지,

커널이 원자적인 갱신 기능을 제공할지,

공유 mutex를 둘지,

현재처럼 참조 횟수와 매핑 순서를 이용할지를 결정할 수 있다.

중요한 것은 어떤 방법이 항상 더 좋다는 결론이 아니다.

**규칙을 내가 기억해서 지키게 할 것인지, 아니면 코드 구조와 상태 전이가 자연스럽게 지키게 할 것인지**를 먼저 결정하는 일이다.

## [정상 코드가 아니라, 약속을 지키는 코드]

이 교육용 운영체제는 상용 운영체제가 아니다.

실제 멀티코어 환경의 메모리 모델, 복잡한 스레드 동기화, 실제 장비의 인터럽트 지연, RTOS의 우선순위·세마포어·ISR을 모두 경험한 것은 아니다.

하지만 이 프로젝트는 이후 시스템을 바라보는 기준을 남겼다.

정상 입력에서 원하는 출력이 나온다고 해서 시스템이 완성되는 것은 아니다.

버퍼가 잠시 비어 있는 순간,

프로세스가 교체되는 순간,

참조 수가 바뀌는 순간,

예외 처리 코드가 다시 예외를 만나는 순간에도 시스템은 약속을 지켜야 한다.

내가 운영체제 구현을 통해 배운 것은 pipe의 EOF 판정 방법이나 MIPS 명령어 자체만은 아니었다.

**코드의 책임은 함수가 반환되는 시점에 끝나지 않는다는 사실**이었다.

내 코드가 만든 상태를 다른 구성요소가 읽을 수 있다면, 그 상태가 잠깐 존재하는 시간까지도 이미 내가 설계해야 할 시스템의 일부였다.

프로그램을 멈추지 않게 하는 것은 정상 코드만이 아니었다.

정상과 오류 사이, 시작과 종료 사이, 내가 직접 보고 있지 않은 중간 상태까지 안전하게 만드는 일이 시스템을 계속 동작하게 만든다는 사실이 이 프로젝트 뒤에 가장 오래 남았다.
