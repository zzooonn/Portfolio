### 3-1. 검색 서비스 (`SearchServiceImpl`)

커밋: `c2fe2f5` 기본 기능 구현(12/14), `05900c3` 단위 테스트 499줄(12/14), `e2fe245` 특허 인용 형식(12/28)

| 기능 | 동작 |
|---|---|
| 검색 조건 데이터 | 성과 유형·학문 분야·기관 목록을 모아 반환한다. 상위 분야가 없는 하위 분야는 걸러낸다. 캐시(`@Cacheable`)와 시간 측정은 이후 Ma-HR이 추가했다(`eace552e`, 12/27). |
| 자연어 검색 해석 | 사용자가 입력한 문장을 LLM 서비스에 넘겨 구조화된 검색 조건으로 바꾼다. **LLM 호출이 실패하면 원문 전체를 본문 검색어로 쓰는 기본 조건으로 대신 반환한다.** |
| 조건 검색 | 검색 조건을 엔티티로 바꿔 저장소에 넘기고 결과를 반환한다. 로그인 사용자면 검색 기록을 저장한다. |
| 검색 기록 저장 | 저장 중 예외는 잡아서 로그만 남긴다. 기록 저장이 실패해도 검색 결과는 돌려주려는 의도다. |
| 인용문 생성 | 논문·특허·기타 성과별로 인용 형식을 만든다. 저자가 3명을 넘으면 줄여 쓴다. 특허는 공개번호, 없으면 신청번호를 쓴다. |
| 검색 기록 조회 | 사용자별 검색 기록을 페이지 단위로 반환한다. |

**단위 테스트 (Mockito, 14개)**: 검색 조건 데이터 반환, 부모 없는 하위 분야 필터링, LLM 호출, **LLM 실패 시 처리**, 로그인 사용자 기록 저장, **비로그인 사용자 기록 미저장**, 빈 검색어 기록 미저장, 성과 없음 예외, 논문 인용 형식, 저자 3명 초과, 저자 없는 논문, 검색 기록 페이지, 빈 기록.

### 3-2. 학자 관계망 (`ScholarNetworkServiceImpl`)

커밋: `0d5bac7` 구현과 단위 테스트(12/14), `41d5d9c` 가중치·집계 로직(12/24), `75cf71d` 첫 조회 시 자동 생성(12/24), `cd3204d` 재조회 시 재계산하지 않음 테스트(12/24), `5f5e1fc` 응답 구조 수정(12/25)

**동작 흐름**
1. 한 학자의 공동 연구 원시 통계(논문·특허·수상별 공동 횟수, 긴밀 협력 횟수, 공동 연구 연도 범위)를 조회한다.
2. 기존 관계 데이터를 지우고, 상대 학자별로 메모리에서 합친다.
3. 가중치를 계산해 `collaboration_edge` 테이블에 저장한다. 공식은 논문 10점, 긴밀 협력 5점, 연도 1점, 특허 15점, 수상 25점이다. **코드 주석상 제품 문서 기준이며 본인이 설계한 공식이 아니다.**
4. 조회할 때 저장된 관계가 없으면 그 자리에서 1~3을 실행하고(첫 조회 시 생성), 있으면 저장본을 그대로 읽는다.
5. 가중치 상위 10명만 고르고, 관련 학자 정보는 한 번에 모아서 조회한다(N+1 조회 방지). 존재하지 않는 학자를 가리키는 관계는 걸러낸다.

**단위 테스트 (Mockito, 9개)**: 관계 없음 → 빈 관계망, 저장본 없음 + 원시 통계 있음 → 생성 후 반환, 학자 없음 → 예외, **재조회 시 원시 통계 조회와 저장이 한 번도 일어나지 않음(`never()` 검증)**, 전체 응답 구성, 없는 학자 관계 걸러내기, 협력 데이터 정확성, 상위 10명 선별, 저장 시 올바른 관계 생성.

**코드에 남긴 판단**: 같은 클래스 안에서 메서드를 부르면 `@Transactional`이 새로 적용되지 않을 수 있지만, 바깥 메서드가 이미 트랜잭션 안이므로 저장이 같은 트랜잭션에서 실행된다는 점을 주석으로 설명했다.

### 3-3. 공고 서비스 (`AnnouncementServiceImpl`)

커밋: `a23016b` 구현과 단위 테스트 6개(12/14), `e511290` 상태 값 수정(12/25), `34782cb` 필드 이름 대소문자 수정(12/25)

- 공고 목록과 상세를 RFC4(팀 API 명세)에 맞춰 반환한다.
- 상태 값을 `DRAFT/PUBLISHED`에서 명세대로 `draft/published`로 바꿨다.
- 명세에서 목록과 상세의 날짜 필드 이름 대소문자(`publishDateTime` / `publishDatetime`)가 달라 **명세 그대로** 맞췄다.
- 없는 공고를 조회할 때 저장소 예외가 Spring에 의해 `JpaObjectRetrievalFailureException`으로 한 번 감싸져 올라오는 경우까지 잡아서, 공고 없음 업무 예외로 바꿨다. Postman으로 확인했다.

### 3-5. 비로그인 사용자 오류 수정과 이후 병합 ⚠️

커밋: `fee70d1`(12/28)

**본인이 한 일**
- 비로그인 상태에서 검색 기록 조회와 검색어 해석을 요청하면, 컨트롤러가 로그인 정보(`principal.uuid()`)를 먼저 꺼내다 null 오류가 났다.
- 서비스 단위 테스트에서는 "비로그인 사용자의 기록은 저장하지 않는다"를 이미 검증하고 있었다. 규칙은 서비스에 있었지만 요청은 서비스까지 닿지 못했다.
- 비로그인이면 검색 기록은 빈 페이지를, 검색어 해석은 사용자 없이 진행하도록 고쳤다. 로그인·비로그인 두 경우를 검증하는 **컨트롤러 테스트 4개**(`OutputSearchControllerTest`)를 새로 만들었다.

**이후 병합에서 바뀐 것 (면접 대비 필수)**
- 다른 팀원이 별도 브랜치에서 비로그인 요청에 **401(Unauthorized)을 던지는 방식**을 먼저 추가해 두었다(Arekaldi `d8a4437`, 12/24).
- 12/28~12/29 병합 과정에서 팀 정책이 401 쪽으로 정리됐다(Ma-HR `dab6aa0`, saitewasreset `9eb222b`).
- 현재 HEAD에서 검색 기록 조회와 검색어 해석은 비로그인이면 401을 반환한다. **본인이 만든 컨트롤러 테스트 파일은 남아 있고, 기대 결과가 401로 바뀌었다.**
- 면접 답변: "제가 고친 시점에는 빈 결과를 돌려주는 방식이었고, 병합하면서 팀이 로그인이 필요한 기능은 401로 통일하기로 했습니다. 제가 만든 컨트롤러 테스트도 그 정책에 맞춰 기대 결과가 바뀌었습니다. 오히려 정책이 바뀌었다는 사실이 테스트 기대 결과에 드러난 사례입니다."

## 4. 본인 코드에서 스스로 짚을 수 있는 한계 (성찰 소재)

모두 **코드 분석으로 찾은 것**이며, 고쳤다고 쓰지 않는다.

| 한계 | 내용 | 연결되는 관점 |
|---|---|---|
| 관계망이 갱신되지 않음 | 저장된 관계망을 다시 만드는 곳은 디버그 API뿐이다. 새 성과가 동기화되어도 기존 관계망은 그대로 남는다. 재계산 금지는 테스트했지만 **언제 다시 만들지**는 정하지 않았다. | 원본과 파생 데이터의 정합성 (DCM 1번 소재) |
| 관계가 없는 학자는 매번 재계산 | 공동 연구가 없는 학자는 저장할 관계가 없어서, 조회할 때마다 원시 통계 조회가 다시 실행된다. "결과 없음"도 결과로 기록하지 않았기 때문이다. | 캐시의 빈 결과 처리 |
| LLM 실패를 조용히 대체 | LLM 해석이 실패하면 원문 검색으로 대체하지만, 응답만 봐서는 호출자가 정상 해석인지 대체 결과인지 구분할 수 없다. | CareLink의 "모르는 값을 조용히 보정하지 않는다"와 대비되는 선택 |
| 기록 저장 예외와 트랜잭션 | 검색과 기록 저장이 같은 트랜잭션 안에 있다. 저장소 쪽에서 예외가 나면 잡더라도 트랜잭션이 롤백 전용으로 표시되어, 커밋 시점에 예외가 날 **가능성**이 있다. 검색 결과를 살리려던 의도가 트랜잭션 경계 때문에 깨질 수 있다. 실제 발생은 확인하지 않았다. | Spring 트랜잭션 전파 이해 |
| 가중치 공식 | 제품 문서의 공식을 그대로 구현했다. 공식 자체의 타당성은 검증하지 않았다. | 과장 방지 |

## 6. 면접 예상 질문과 답변 골격

**Q. 이 프로젝트에서 본인은 무엇을 맡았나요?**
검색 서비스, 학자 관계망, 공고 서비스를 구현했고 성과 상세의 작성자 목록과 응답 구조 정리를 맡았습니다. 맡은 서비스마다 Mockito 단위 테스트를 작성했습니다. 조회수 집계나 외부 데이터 동기화는 다른 팀원이 맡았습니다.

**Q. 관계망을 왜 매번 계산하지 않고 저장했나요?**
관계망은 한 학자의 모든 공동 성과를 집계해야 해서 조회할 때마다 계산하면 부담이 큽니다. 그래서 첫 조회 때 계산해 저장하고 이후에는 저장본을 읽게 했고, 재조회 때 다시 계산하지 않는다는 점을 테스트로 확인했습니다.

**Q. 그럼 새 논문이 들어오면 관계망은 어떻게 되나요?**
현재 구조에서는 갱신되지 않습니다. 디버그 API로만 다시 만들 수 있습니다. 다시 만든다면 성과가 저장되는 시점에 관련 학자의 관계망을 무효화하거나, 관계망에 생성 시각을 두고 일정 주기로 재계산할 것입니다. 재계산 금지만 테스트하고 재계산 조건은 정의하지 않았다는 것이 이 기능의 가장 큰 교훈입니다.

**Q. 비로그인 오류는 어떻게 찾았나요? 지금 코드와 다르던데요.**
서비스 테스트는 비로그인 규칙을 검증하고 있었는데, 실제로는 컨트롤러가 로그인 정보를 먼저 꺼내다 실패했습니다. 빈 결과를 돌려주도록 고치고 컨트롤러 테스트를 추가했습니다. 이후 병합에서 팀이 로그인 필요 기능을 401로 통일해 지금 코드는 401을 반환하고, 제 테스트도 그 기대 결과로 바뀌었습니다.

**Q. LLM이 실패하면 어떻게 되나요?**
원문 전체를 본문 검색어로 쓰는 기본 조건으로 대신 반환합니다. 사용자는 검색 결과를 받을 수 있지만, 응답만으로는 해석 성공인지 대체인지 구분할 수 없는 한계가 있습니다. 대체 여부를 응답에 표시하는 것이 개선 방향입니다.

**Q. 없는 공고를 조회하면 어떻게 되나요?**
업무 예외로 바꿔 반환합니다. 저장소 예외가 Spring에서 다른 예외로 감싸져 올라오는 경우가 있어서 두 경우를 모두 잡았습니다. 예외가 계층을 지나면서 형태가 바뀔 수 있다는 것을 이때 확인했습니다.

## 7. 팀 전체 구조 (본인 작성 아님 — 분석 참고용)

> 이 절은 팀 코드를 이해하기 위한 요약이다. 자소서에서는 "팀 구조를 분석했다" 수준으로만 쓴다.

### 7-1. 시스템 구성

```text
브라우저 (Vue 3)
  └─ /api 요청 ─→ Spring Boot 백엔드
                    ├─ Controller → Service → Repository
                    ├─ PostgreSQL   : 원본 데이터 (계정·학자·기관·성과·요청·분석)
                    ├─ Elasticsearch: 검색 색인 (제목·초록·키워드·임베딩)
                    ├─ Redis        : 캐시, 조회수 임시 집계, ORCID 상태
                    ├─ MinIO        : 아바타 파일
                    └─ 외부 연동    : OpenAlex, ORCID, LLM, 벡터 임베딩 서버
```

### 7-2. 저장소 역할

| 저장소 | 역할 | 일관성 | 담당 |
|---|---|---|---|
| PostgreSQL | 원본 | 관계형 제약 | 팀 공동 |
| Elasticsearch | 검색용 조회 모델 | PostgreSQL과 최종 일관성 | 팀 공동 |
| Redis | 캐시·조회수·ORCID 상태 | TTL·배치 반영에 의존 | Ma-HR(캐시), saitewasreset(조회수), Arekaldi(ORCID) |
| MinIO | 아바타 파일 | DB 메타데이터와 분리 | Arekaldi |

### 7-3. 팀 코드에서 확인되는 위험 (분석 결과, 본인 작성 아님)

| 위험 | 내용 | 코드 작성자 |
|---|---|---|
| 조회수 중복·유실 | Redis 증가분을 가져간 뒤 DB 반영이 실패하면 유실되고, 반영 후 차감이 실패하면 중복된다. 중복 방지 키에 성과 식별자가 없다. | saitewasreset |
| 색인 거짓 완료 | PostgreSQL 저장 트랜잭션이 끝난 뒤 Elasticsearch 색인이 실패해도 작업이 완료로 표시될 수 있다. | Ma-HR |
| 전체 허용 보안 설정 | `SecurityConfig`가 모든 요청을 허용하고 컨트롤러에서 수동으로 검사한다. 검사를 빠뜨리면 보호되지 않는다. | 팀 공동 |
| 프론트 목업 대체 | 설정값에 따라 오류 응답이 데모 데이터로 표시될 수 있다. | 프론트엔드 팀 |
| ORCID 상태 순서 | DB 연결보다 성공 상태가 먼저 기록될 수 있다. | Arekaldi |
| 테스트용 스키마 차이 | 운영 Flyway와 테스트 H2 스키마가 달라, 테스트 통과 후 운영 기동에서 실패할 가능성이 있다. | 팀 공동 |

이 표는 면접에서 "팀 프로젝트의 다른 부분도 이해하고 있는가"에 답하는 용도다. **"제가 찾아서 고쳤다"로 쓰지 않는다.**

### 7-4. 협업 구조

- RFC 문서(RFC1: 협업 규칙, RFC3~5: 요구사항·API·DB)로 API와 DB를 합의했다.
- 작업 단위(Task)를 화웨이 CodeHub에 등록하고, 한 병합 요청은 한 담당자의 작업만 닫는 규칙을 썼다(RFC1).
- 본인은 RFC4 명세에 맞춰 공고·성과 상세 응답을 정렬하는 작업을 여러 번 했다(3-3, 3-4).
