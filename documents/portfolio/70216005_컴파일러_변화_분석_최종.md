## 1. 과제 목표와 전체 개발 방향

`编译技术.pdf`의 전체 흐름은 다음 네 단계로 구성되어 있다.

1. 词法分析, 즉 어휘 분석
2. 语法分析, 즉 구문 분석
3. 语义分析, 즉 의미 분석
4. 代码生成, 즉 코드 생성과 실행

처음에는 단순히 `testfile.txt`를 읽고 토큰을 출력하는 수준이었다. 그러나 과제가 진행될수록 컴파일러는 다음 기능을 모두 수행해야 했다.

- 소스 코드를 토큰 단위로 분해한다.
- 문법 규칙에 맞추어 비단말 기호를 분석한다.
- 문법 오류, 의미 오류를 정확한 줄 번호와 오류 코드로 출력한다.
- 심볼 테이블을 관리한다.
- 함수, 배열, 상수, 스코프, return, break/continue 등을 검사한다.
- P-code를 생성한다.
- 생성된 P-code를 인터프리터로 실행한다.

이 과정에서 가장 어려웠던 부분은 단순한 토큰 인식이 아니라 오류 복구였다. 특히 `i`, `j`, `k` 오류는 실제 입력에 토큰이 존재하지 않는 오류이기 때문에, 파서가 현재 토큰을 잘못 소비하면 이후 문장 전체가 밀려 버린다.

오류 코드는 다음과 같이 해석된다.

| 오류 코드 | 의미 |
|---|---|
| `i` | 세미콜론 `;` 누락 |
| `j` | 오른쪽 소괄호 `)` 누락 |
| `k` | 오른쪽 대괄호 `]` 누락 |

이 세 오류는 겉으로 보기에는 단순하지만, 실제 구현에서는 구조 변경의 핵심 압력 중 하나가 될 정도로 큰 영향을 주었다.

### 3.2 토큰 종류 정의

2단계에서 가장 먼저 생긴 것은 토큰 종류이다.

```cpp
enum TokenType {
    IDENFR, INTCON, STRCON, CHRCON, MAINTK, CONSTTK, INTTK, CHARTK, BREAKTK,
    CONTINUETK, IFTK, ELSETK, FORTK, GETINTTK, GETCHARTK, PRINTFTK, RETURNTK,
```

이 enum은 PDF의 어휘 분석 표와 대응된다. 키워드, 식별자, 정수 상수, 문자열 상수, 문자 상수, 연산자, 구분자를 모두 구분한다.


### 3.5 주석 처리

`/`는 나눗셈일 수도 있고, `//`, `/* */` 주석의 시작일 수도 있다. 그래서 2단계에서는 `/`를 특별히 먼저 처리한다.

```cpp
else if(currentChar == '/')
{
    char nextChar = inputFile.peek();

    if(nextChar == '*')
    {
        inputFile.get();
        bool endofComment = false;

        while(inputFile.get(currentChar))
        {
            if(currentChar == '\n')
            {
                lineNumber++;
            }
            else if(currentChar == '*')
            {
                if(inputFile.peek() == '/')
                {
                    inputFile.get();
                    endofComment = true;
                    break;
                }
            }
        }
        continue;
    }
    else if(nextChar == '/')
    {
        inputFile.get();
        while(inputFile.get(currentChar))
        {
            if(currentChar == '\n' || currentChar == '\r')
            {
                lineNumber++;
                break;
            }
        }
        continue;
    }
    else
    {
        tokens.push_back({DIV, "/", lineNumber});
    }
}
```

이 부분은 이후 단계에서도 거의 유지된다. 컴파일러의 첫 단계인 어휘 분석에서 주석은 토큰으로 남기지 않고 제거해야 하기 때문이다.

### 3.6 단일 `&`, `|` 오류

2단계에서 어휘 오류의 대표적인 예는 단일 `&`, 단일 `|`이다. 과제 문법에서는 논리 연산자로 `&&`, `||`만 허용되기 때문에 단일 문자는 `a` 오류가 된다.

```cpp
if (currentChar == '&') 
{
    if(nextChar == '&')
    {
        op += inputFile.get();
        tokens.push_back({AND, op, lineNumber});
    }
    else
    {
        errors.push_back({lineNumber, 'a'});
    }
}
else if (currentChar == '|') 
{
    if(nextChar == '|')
    {
        op += inputFile.get();
        tokens.push_back({OR, op, lineNumber});
    }
    else
    {
        errors.push_back({lineNumber, 'a'});
    }

```

2단계의 한계는 명확하다. 어휘 분석만 하기 때문에 `;`, `)`, `]`가 빠진 경우를 판단할 수 없다. `i/j/k`는 문법 구조를 알아야만 감지할 수 있다.

또 하나의 실제 파일상 한계는 `config.json`이다. 2단계부터 최종 `CMakeLists`까지 `config.json`에는 `"programming language": "cpp"`와 `"object code": "pcode"`가 들어 있지만, 실제 C++ 코드에는 이 JSON을 읽는 로직이 없다. 따라서 이 파일은 실행 옵션이라기보다 제출 메타데이터에 가깝고, P-code 출력 여부는 설정 파일이 아니라 각 단계의 하드코딩된 파이프라인으로 결정된다.

### 4.4 3단계의 `i/j/k` 처리

3단계에서 처음으로 `i`, `j`, `k` 오류가 명시적으로 구현된다.

```cpp
void parseErrorPrintfI() {
    Token currentToken = getCurrentToken();
    Token previousToken = getPreviousToken();

    if (currentToken.type == SEMICN) {
        outputToken(currentToken);
        advanceToken();
    }
    else {
        errors.push_back({ previousToken.lineNumber, 'i' });
    }
}

void parseErrorPrintfJ() {
    Token currentToken = getCurrentToken();
    Token previousToken = getPreviousToken();

    if (currentToken.type == RPARENT) {
        outputToken(currentToken);
        advanceToken();
    }
    else {
        errors.push_back({ previousToken.lineNumber, 'j' });
    }
}

void parseErrorPrintfK() {
    Token token = getCurrentToken();

    if (token.type == RBRACK) {
        outputToken(token);
        advanceToken();
    }
    else {
        errors.push_back({ token.lineNumber, 'k' });
    }
}
```

여기서 중요한 점은 `i`와 `j`는 이전 토큰의 줄 번호를 사용하고, `k`는 현재 토큰의 줄 번호를 사용하고 있다는 점이다. 이 방식은 초기에 어느 정도 동작하지만, 뒤 단계로 갈수록 부족해진다.

왜냐하면 실제 채점 기준에서는 `i/j/k`의 줄 번호가 “직전 비단말 또는 직전 의미 있는 토큰”에 따라 달라져야 하는 경우가 많기 때문이다. 단순히 `previousToken` 또는 `currentToken`만 보면 안 되는 상황이 생긴다.

### 4.5 `parseStmt()`의 복잡화

3단계에서 가장 복잡해진 함수는 `parseStmt()`이다.

```cpp
void parseStmt() {
    Token token = getCurrentToken();

    if (token.type == BREAKTK) {
        outputToken(token);
        advanceToken();
        token = getCurrentToken();

        if (token.type == SEMICN) {
            outputToken(token);
            advanceToken();
        }
        else {
            parseErrorPrintfI();
        }
    }
    else if (token.type == CONTINUETK) {
        outputToken(token);
        advanceToken();

        if (getCurrentToken().type == SEMICN) {
            outputToken(getCurrentToken());
            advanceToken();
        }
        else {
            parseErrorPrintfI();
        }
    }
    else if (token.type == RETURNTK) {
        outputToken(token);
        advanceToken();

        if (getCurrentToken().type != SEMICN) {
            parseExp();
        }

        if (getCurrentToken().type == SEMICN) {
            outputToken(getCurrentToken());
            advanceToken();
        }
        else {
            parseErrorPrintfI();
        }
    }
}
```

따라서 `for`문 안에서는 `i`와 `j`가 동시에 얽힌다.

- 이 상태에서 라벨과 점프 코드를 만들면 P-code가 틀어진다.

그래서 `for`는 5단계 성공률을 낮춘 주요 원인 중 하나이다.

### 6.10 5단계가 100%에 도달하지 못한 구조적 원인

5단계에서 100%에 도달하지 못한 이유는 단일 버그 하나가 아니라 구조적인 문제이다.

가장 큰 원인은 다음과 같다.

1. 파싱, 오류 복구, 의미 검사, P-code 생성이 한 함수 안에 섞여 있었다.
2. `i/j/k`가 누락 오류라서 토큰 소비 여부가 매우 중요한데, 각 문법 함수마다 처리 방식이 달랐다.
3. `mLastNonT`를 정확히 갱신하지 않으면 줄 번호가 틀어졌다.
4. `j` 오류가 발생한 뒤에도 `d/e` 같은 의미 검사가 이어지면 잘못된 오류가 추가될 수 있었다.
5. `k` 오류가 배열 주소 계산과 연결되어 P-code 생성까지 흔들었다.
6. `for`문 내부의 `i/j` 오류가 라벨 생성과 결합되어 복구가 어려웠다.
7. 단일 파일이 너무 커져서 한 부분을 고치면 다른 부분이 깨졌다.

결론적으로 `i/j/k` 때문에 5단계 구조로 바뀌었다고 해도 과장이 아니며, 동시에 `i/j/k` 때문에 5단계 단일 파일 구조가 한계에 부딪혔다고 볼 수 있다.

### 7.1 구조 변화

최종 제출 구조는 다음과 같다.

5단계에서는 모든 코드가 `70216005-5.cpp` 하나에 들어 있었지만, 최종 구조에서는 역할별로 파일이 나누어졌다. 실제 폴더에는 `build/` 산출물도 함께 존재하지만, 분석 대상이 되는 구조적 변화는 위 소스 파일과 `config.json`이다. 생성된 `build/` 디렉터리는 환경별 절대 경로가 들어갈 수 있으므로 최종 구조의 본질로 보기는 어렵다.

### 7.2 CMake 설정

최종 구조는 CMake로 빌드되도록 바뀌었다.

```cmake

```

실제 `CMakeLists.txt`에는 위 목록 외에도 Windows와 비 Windows 모두에서 `clang`, `clang++`를 지정하려는 `if(WIN32) ... else()` 블록이 있다. 다만 이 설정은 `project(Compiler)` 뒤에 오기 때문에 CMake 관점에서는 컴파일러 선택을 완전히 보장하는 위치는 아니다. 그럼에도 단일 cpp나 Visual Studio 프로젝트 파일에 기대던 단계보다, 어떤 소스들을 묶어 `Compiler` 실행 파일을 만들지 명시했다는 점에서 빌드 재현성은 좋아졌다.

이 변화는 단순히 빌드 방식을 바꾼 것이 아니다. 컴파일러의 기능을 모듈 단위로 분리해서 디버깅 가능하게 만들기 위한 변화이다.

### 7.3 최종 main 파이프라인

`ComplierSysY.cpp`는 전체 흐름을 명확히 보여준다.

```cpp
int main()
{
    // 词法分析
    auto pLexer = make_shared<Lexer>("testfile.txt");
    pLexer->LexicalAnalysis2();
    pLexer->WriteToFile("lexer.txt");
    const vector<TokenWord>& tokens = pLexer->GetTokenList();

    // 语法分析
    shared_ptr<Parser> pParser = make_shared<Parser>(tokens);
    pParser->SyntaxAnalysis();
    pParser->WriteToFile("pcode.txt");
    auto pErrorHandler = pParser->GetErrorHandler();
    if (pErrorHandler && pErrorHandler->HasError())
    {
        pErrorHandler->PrintErrorList("error.txt");
    }

    // 解释执行
    shared_ptr<Interpreter> pInterpreter = make_shared<Interpreter>();
    pInterpreter->Inter(pParser->GetCodeList());
    pInterpreter->WriteToFile("pcoderesult.txt");

    return 0;
}
```

이 코드는 전체 컴파일러를 세 단계로 분리한다.

1. `Lexer`: 어휘 분석
2. `Parser`: 구문 분석, 의미 분석, P-code 생성
3. `Interpreter`: P-code 실행

여기서 실제 동작상 중요한 차이가 하나 있다. `70216005-5.cpp`의 `main()`은 `ErrorHandler`에 오류가 있으면 `error.txt`를 출력하고 `return 0`으로 인터프리터 실행을 중단한다. 반면 최종 `CMakeLists/ComplierSysY.cpp`는 오류가 있어도 `PrintErrorList("error.txt")`를 호출한 뒤 `Interpreter`를 계속 실행한다. 따라서 최종 구조는 파일 분리뿐 아니라 오류 발생 후 실행 정책도 일부 달라졌다.

### 7.4 ErrorHandler 분리

5단계에서는 오류 처리가 Parser 내부 클래스처럼 들어 있었지만, 최종 구조에서는 `ErrorHandler`가 별도 파일로 분리된다.

```cpp
struct ErrorWord {
    int linenum;
    char err_type;
};

class ErrorHandler 
{
public:
    bool HasError() { return !mErrorList.empty(); };
private:
    std::vector<ErrorWord> mErrorList;

public:
    void PushErrorList(char err_type, int err_line);
    void PrintErrorList(std::string_view filePath);
};
```

오류 추가와 출력도 분리되었다.

```cpp
void ErrorHandler::PushErrorList(char err_type, int err_line) {
    ErrorWord error;
    error.linenum = err_line;
    error.err_type = err_type;
    mErrorList.push_back(error);
}

void ErrorHandler::PrintErrorList(std::string_view filePath)
{
    std::sort(mErrorList.begin(), mErrorList.end(), [](const ErrorWord& a, const ErrorWord& b) {
        if (a.linenum == b.linenum) 
        {
            return a.err_type > b.err_type;
        }
        return a.linenum < b.linenum;
    });

    std::fstream outFile(filePath.data(), std::ios::trunc | std::ios::out);
    if (outFile.good())
    {
        int last_line = -1;
        for (const auto& error : mErrorList) 
        {
            if (error.linenum != last_line)
            {
                outFile << error.linenum << " " << error.err_type;
                std::cout << error.linenum << " " << error.err_type << std::endl;
                last_line = error.linenum;
            }
        }
    }
}
```

이 구조의 장점은 Parser가 오류 출력 형식을 직접 신경 쓰지 않아도 된다는 점이다.

단, 최종 `ErrorHandler`는 4단계의 `errorLines` 방식처럼 저장 시점에 중복 줄을 막지 않는다. 모든 오류를 `mErrorList`에 넣은 뒤 줄 번호순으로 정렬하고, 같은 줄에서는 `err_type` 내림차순으로 정렬한 다음 첫 오류만 출력한다. 즉 “먼저 들어온 오류만 저장”하던 4단계 방식과, “모아 둔 뒤 정렬 후 한 줄당 하나만 출력”하는 최종 방식은 다르다. 이 차이 때문에 최종 구조에서는 오류 우선순위가 `ErrorHandler::PrintErrorList()`의 정렬 기준에도 의존한다.

## 8. `i/j/k` 오류가 구조 변경의 핵심 원인이 된 이유

### 8.1 `i/j/k`는 존재하지 않는 토큰을 처리하는 오류이다

대부분의 오류는 잘못된 토큰을 보고 판단할 수 있다.

예를 들어 단일 `&`는 입력에 실제로 존재한다.

```c
if (a & b)
```

하지만 `i/j/k`는 다르다.

```c
a = 1
```

여기에는 `;`가 없다. 즉 파서는 없는 토큰을 보고 오류를 내야 한다.

```c
if (a > b {
```

여기에는 `)`가 없다.

```c
a[1 = 3;
```

여기에는 `]`가 없다.

이런 오류는 “현재 토큰이 틀렸다”가 아니라 “현재 토큰 앞에 무언가 빠졌다”이다. 그래서 현재 토큰을 소비하면 안 되는 경우가 많다.

### 8.2 `i`는 문장 경계를 무너뜨린다

`i` 오류는 세미콜론 누락이다. 세미콜론은 문장의 끝을 의미한다. 따라서 `;`가 없으면 파서는 어디까지가 현재 문장이고 어디부터가 다음 문장인지 판단하기 어려워진다.

예를 들어 다음 코드를 보자.

```c
a = 1
b = 2;
```

올바른 오류는 첫 줄의 `i`이다. 하지만 파서가 `b`까지 현재 문장의 일부로 읽어 버리면 이후 문장이 전부 깨진다.

5단계에서는 이를 막기 위해 줄 번호가 바뀌는지 확인하는 로직까지 들어갔다.

```cpp
int tempLineNumber = mCurToken.lineNum;
while (true)
{
    if (mCurToken.word == ";")
        break;
    if (mCurToken.word == "=")
    {
        isLVal = 1;
        break;
    }
    if (tempLineNumber != mCurToken.lineNum) {
        parseErrorI();
    }
    index++;
    AdvanceToNextToken();
}
```

이런 방식은 문제를 해결하려는 시도였지만, 동시에 파서 상태를 더 불안정하게 만들었다. 전방 탐색 중에 토큰을 움직였다가 다시 되돌려야 했기 때문이다.

### 8.3 `j`는 오류 우선순위를 만든다

`j`는 `)` 누락이다. 이 오류는 함수 호출과 강하게 연결된다.

```c
foo(a, b;
```

이 경우 `)`가 없으므로 `j` 오류가 핵심이다. 그런데 함수 호출에는 인자 개수 검사 `d`, 인자 타입 검사 `e`도 있다. 만약 `)`가 없는 상태에서 인자 검사를 계속하면 잘못된 오류가 추가된다.

그래서 5단계와 CMake 구조에서는 다음처럼 처리한다.

```cpp
if (!parseErrorJ()) {
    if (mFuncparse.back().expectedcnt != mFuncparse.back().paramcnt) {
        parseErrorD(mLastFuncLine);
    }
}
```

즉 `parseErrorJ()`가 오류를 발견하면 뒤의 `d` 검사를 하지 않는다.

이처럼 `j`는 단순한 괄호 오류가 아니라, 다른 오류의 발생 여부까지 제어하는 기준이 된다.

### 8.4 `k`는 배열 주소 계산을 무너뜨린다

`k`는 `]` 누락이다. 배열에서는 `]`가 있어야 배열 인덱스 표현식의 끝을 알 수 있다.

```c
a[i = 3;
```

이 경우 `i = 3`을 배열 인덱스 표현식으로 읽어야 하는지, 대입문으로 읽어야 하는지 애매해진다.

5단계에서는 배열 접근이 곧 P-code 주소 계산과 연결되어 있다.

```cpp
if (mCurToken.word == "[") {
    isarr = true;

    mLastNonT = mCurToken.lineNum;
    AdvanceToNextToken();

    type = ParseExp();

    parseErrorK();
}
```

그리고 바로 다음에 주소 계산 코드가 나온다.

```cpp
auto code1 = std::make_shared<PCode>("LOD_A", global, addr);
mCodelist.push_back(code1);
auto code2 = std::make_shared<PCode>("ADD");
mCodelist.push_back(code2);
```

즉 `k`가 틀리면 단순히 오류 출력만 틀리는 것이 아니라 P-code 자체가 틀릴 수 있다.

## 9. 왜 결국 CMake 구조로 바꿀 수밖에 없었는가

### 9.1 5단계 단일 파일 구조의 한계

5단계는 기능적으로 많은 것을 담고 있었다.

- Lexer
- ErrorHandler
- SymbolTableManager
- Parser
- Interpreter
- PCode
- PCodeLabel
- Value

하지만 이 모든 것이 하나의 `70216005-5.cpp` 안에 있었다. 그래서 다음 문제가 생겼다.

1. 오류 하나를 고치려면 전체 파일을 봐야 했다.
2. Parser와 Interpreter의 책임이 분리되지 않았다.
3. `i/j/k` 오류 복구와 P-code 생성이 한 함수 안에 섞였다.
4. `mCurToken`, `mCurpos`, `mLastNonT`가 여러 함수에서 동시에 변경됐다.
5. 전방 탐색 후 되돌아오는 코드가 많아져 토큰 위치 추적이 어려워졌다.
6. 오류 우선순위가 명확히 분리되지 않았다.
7. 디버깅이 어려워져 성공률을 끝까지 끌어올리기 어려웠다.

### 9.2 CMake 구조의 목적

CMake 구조의 목적은 빌드 도구 변경만이 아니다. 더 중요한 목적은 책임 분리이다.

| 모듈 | 책임 |
|---|---|
| `Lexer` | 토큰 생성 |
| `Parser` | 구문 분석, 의미 분석, P-code 생성 |
| `ErrorHandler` | 오류 저장, 정렬, 출력 |
| `SymbolTableManager` | 심볼 저장, 검색 |
| `Interpreter` | P-code 실행 |
| `DataDef` | 공통 자료구조 |

이렇게 나누면 `i/j/k` 오류를 고칠 때 적어도 오류 출력은 `ErrorHandler`, 토큰 이동은 `Parser`, 심볼 문제는 `SymbolTableManager`, 실행 문제는 `Interpreter`로 분리해서 볼 수 있다.

다만 이것은 완전한 컴파일러 계층 분리가 아니라 현실적인 파일 분리이다. 최종 `Parser`는 여전히 구문 분석, 의미 검사, P-code 생성, 상수식 계산, 함수 호출 정보 관리, 루프 라벨 관리까지 함께 담당한다. 즉 `CMakeLists` 구조의 핵심은 `Parser`의 모든 책임을 해체한 것이 아니라, `Lexer`, 오류 출력, 심볼 저장, P-code 실행기를 밖으로 빼서 5단계 단일 파일보다 추적 가능한 구조로 만든 데 있다.

### 9.3 `i/j/k` 관점에서 CMake 구조가 더 나은 이유

CMake 구조에서도 `i/j/k`는 여전히 `Parser` 안에 있다.

```cpp
bool Parser::parseErrorI()
{
    if (mCurToken.word != ";") {
        m_pErrorHandler->PushErrorList('i', mLastNonT);
        return true;;
    }
    else {
        AdvanceToNextToken();
    }
    return false;
}

bool Parser::parseErrorJ()
{
    if (mCurToken.word != ")") {
        m_pErrorHandler->PushErrorList('j', mLastNonT);
        return true;
    }
    else {
        AdvanceToNextToken();
    }
    return false;
}

void Parser::parseErrorK()
{
    if (mCurToken.word != "]") {
        m_pErrorHandler->PushErrorList('k', mLastNonT);
    }
    else {
        AdvanceToNextToken();
    }
}
```

하지만 5단계와 달리 오류 저장/출력은 `ErrorHandler`로 분리되었다. 이 차이가 크다.

5단계에서는 파서 코드 안에서 오류 저장 방식과 출력 방식까지 같이 봐야 했다. CMake 구조에서는 `Parser`가 오류를 발견하면 `PushErrorList()`만 호출하면 된다. 오류 정렬, 중복 줄 처리, 파일 출력은 `ErrorHandler`가 담당한다.

### 9.4 최종적으로 바꾸게 된 핵심 원인

정리하면 CMake 구조로 바꿀 수밖에 없었던 원인은 다음과 같다.

1. 5단계에서 P-code 생성까지 들어오면서 `i/j/k` 오류 복구가 지나치게 복잡해졌다.
2. 누락 오류는 현재 토큰을 소비하지 않는 방식으로 처리해야 하는데, 단일 파일 구조에서는 이 규칙이 일관되게 유지되기 어려웠다.
3. `j` 오류는 `d/e` 오류와 우선순위를 가져야 했고, 이를 함수마다 따로 관리해야 했다.
4. `k` 오류는 배열 주소 계산과 직접 연결되어 P-code까지 흔들었다.
5. `i` 오류는 문장 경계를 무너뜨려 전방 탐색과 토큰 복구를 어렵게 했다.
6. 오류 처리, 심볼 처리, 코드 생성, 실행이 모두 한 파일에 있어 디버깅이 거의 불가능해졌다.
7. 따라서 최종 제출에서는 모듈별로 책임을 나누는 구조가 필요했다.

### 10.2 실제 파일 대조로 보강해야 하는 부분

1단계 테스트는 기존 문서에 적힌 예시보다 더 많은 요구를 담고 있다. `testfile1.txt`의 전역 문자 배열과 `findMax()`, `testfile2.txt`의 문자열 출력/함수 반복 호출, `testfile3.txt`와 `testfile6.txt`의 여러 `for` 생략 형태, `testfile5.txt`의 입력 함수와 단항 연산까지 포함해야 한다. 그래서 최종 구조 변경의 압력은 `i/j/k`만이 아니라 배열, 함수 호출, 루프 제어, 입력/출력, P-code 메모리 모델이 함께 커진 결과이다.

2단계부터 최종 구조까지 있는 `config.json`은 실제 코드에서 읽히지 않는다. 따라서 `"object code": "pcode"`는 실행 설정이 아니라 제출용 메타데이터에 가깝다. 실제 P-code 생성은 `Parser` 내부 코드와 `pParser->WriteToFile("pcode.txt")` 호출로 결정된다.

4단계 분석은 루트의 `실험/70216005-4/bianyi.cpp`를 기준으로 삼는 것이 맞다. 폴더 안에는 `99%/bianyi.cpp`와 여러 zip 버전도 있지만, 기존 문서가 명시한 주요 경로는 루트 파일이다. 5단계도 같은 이유로 루트의 `실험/70216005-5/70216005-5.cpp`를 기준으로 보는 것이 일관적이다. Visual Studio 프로젝트 내부의 `소스.cpp`나 zip들은 실험 흔적 또는 다른 버전으로 분리해서 봐야 한다.

최종 `CMakeLists` 구조의 `DataDef.h`는 `std::vector`를 사용하지만 `<vector>`를 직접 include하지 않는다. 현재는 `Parser.h`나 `Interpreter.h`가 먼저 `<vector>`를 include하기 때문에 빌드될 수 있지만, 헤더 자체의 자립성은 약하다. 이것은 모듈화가 되었더라도 아직 완전히 정리된 설계는 아니라는 근거다.

최종 `ComplierSysY.cpp`는 `_WINDOWS_DEBUG`가 정의된 경우 실행 파일 디렉터리로 현재 작업 디렉터리를 바꾸는 Windows 전용 코드를 포함한다. 이는 `testfile.txt`, `lexer.txt`, `pcode.txt`, `error.txt`, `pcoderesult.txt` 같은 상대 경로 파일을 실행 위치 기준으로 찾게 하려는 보조 코드다. 기존 문서의 main 예시는 핵심 파이프라인만 보여주기 위해 이를 생략한 것이므로, 실제 파일 설명에서는 이 차이를 적어 두는 편이 정확하다.

최종 구조에서 오류가 있어도 인터프리터가 계속 실행되는 점은 특히 주의해야 한다. `70216005-5.cpp`는 오류가 있으면 `print_err_list("error.txt")` 뒤 `return 0`으로 멈췄지만, `CMakeLists/ComplierSysY.cpp`는 오류 출력 뒤에도 `pInterpreter->Inter()`를 호출한다. 따라서 최종 구조는 “오류와 실행을 분리했다”는 점에서는 좋아졌지만, “오류 시 실행 정책”은 5단계와 완전히 동일하지 않다.

### 10.3 최종 판단

기존 md의 중심 주장, 즉 “`i/j/k` 누락 오류와 P-code 생성이 얽히면서 단일 파일 구조가 한계에 도달했고, 최종적으로 CMake 기반 모듈 구조가 필요해졌다”는 설명은 실제 코드와 교재 흐름에 대체로 부합한다. 그러나 더 완벽하게 맞추려면 다음처럼 정리해야 한다.

1. `i/j/k`는 핵심 원인이지만 유일한 원인은 아니다. 배열 주소, 함수 호출, `for` 라벨, 심볼표, P-code 실행기까지 함께 커졌다.
2. `CMakeLists`는 빌드 파일 이름이 아니라 최종 소스 폴더 이름이며, 실제 변화는 다중 소스 빌드와 책임 분리다.
3. 최종 구조는 완전한 전단/후단 분리가 아니라 `Parser` 중심 구조에서 주변 책임을 분리한 현실적 모듈화다.
4. `config.json`은 현재 코드 동작을 바꾸지 않는다.
5. 최종 `ErrorHandler`는 저장 시점 중복 제거가 아니라 정렬 후 한 줄당 하나만 출력하는 방식이다.
6. 최종 main은 5단계와 달리 오류가 있어도 인터프리터를 계속 실행한다.

이 보강까지 반영하면 문서는 실제 `70216005-1`부터 `70216005-5`, 최종 `CMakeLists`, 그리고 `编译技术.pdf`의 설명과 더 정확히 일치한다.

## 11. 일반 컴파일러와의 구조 비교: 이 프로젝트는 "컴파일러 흉내를 낸 인터프리터"이다

### 11.1 일반 컴파일러의 4단계와 이 프로젝트의 3단계

흔히 말하는 일반 컴파일러(예: GCC)의 처리 흐름은 다음과 같다.

```text
전처리(Preprocess) → 컴파일(Compile) → 어셈블(Assemble) → 링크(Link) → 실행 파일(.exe)
```

반면 이 프로젝트의 `ComplierSysY.cpp` `main()`은 다음 세 단계뿐이다.

```text
Lexer(어휘 분석) → Parser(구문/의미 분석 + P-code 생성) → Interpreter(P-code 직접 실행)
```

두 흐름을 대응시키면 다음 표와 같다.

| 일반 컴파일러 단계 | 이 프로젝트 | 비고 |
|---|---|---|
| 전처리(Preprocess) | 없음 | `#include`, 매크로 전개 같은 전처리 단계가 없다 |
| 컴파일(Compile) | 있음 (`Lexer` + `Parser`) | 어휘/구문/의미 분석과 중간코드 생성이 여기에 해당 |
| 어셈블(Assemble) | 없음 | 실제 기계어(어셈블리)로 번역하지 않는다 |
| 링크(Link) | 없음 | 여러 목적 파일을 합쳐 실행 파일을 만들지 않는다 |
| 최종 산출물 = `.exe` | 최종 산출물 = 실행 결과(`pcoderesult.txt`) | 번역이 아니라 "그 자리에서 실행한 답"을 낸다 |

즉 이 프로젝트는 일반 컴파일러의 앞부분(어휘/구문/의미 분석)은 공유하지만, 뒷부분(어셈블·링크로 네이티브 실행 파일을 만드는 과정)이 존재하지 않는다.

### 11.2 핵심 차이: 번역이 아니라 해석이다

일반 컴파일러는 소스 코드를 **네이티브 기계어로 번역해 실행 파일로 남기고 끝난다.** 실행은 나중에 운영체제와 CPU가 별도로 수행한다.

그러나 이 프로젝트는 `Parser`가 만든 P-code를 실제 기계어로 번역하지 않는다. 대신 `Interpreter`가 그 P-code를 **한 명령씩 읽으며 그 자리에서 직접 실행**해 결과를 만든다. 따라서 이 프로젝트는 이름은 "Compiler"이지만, 동작 성격상으로는 **컴파일러(전단) + 가상 기계(후단 실행기)를 합친 인터프리터**에 더 가깝다.

`Interpreter.h`의 다음 멤버가 그 근거다.

```cpp
std::array<int, 100001> mDStack;   // 실행용 데이터 스택 (가상 기계의 메모리)
int BAddr = 0;                     // 현재 함수 프레임 기준 주소(base)
int sp = -1;                       // 스택 포인터
int mainBAddr = 0;
```

`mDStack`과 `sp`, `BAddr`는 실제 CPU가 아니라 **소프트웨어로 흉내 낸 스택 기계**다. 이 구조는 Java의 JVM이 바이트코드를 실행하거나 Python 인터프리터가 자체 명령을 실행하는 방식과 본질적으로 동일하다. P-code는 그 가상 기계에서만 통용되는 "가상 명령어"이며, 진짜 CPU에는 존재하지 않는다.

### 11.3 P-code 명령어 집합(가상 명령어 목록)

`Interpreter::Inter()`가 실제로 해석하는 P-code 명령어는 다음과 같다. 이는 진짜 CPU 명령어가 아니라, 이 프로젝트 안에서만 약속된 가상 명령어 집합이다.

| 분류 | 명령어 | 의미 |
|---|---|---|
| 스택 공간 | `INT`, `INT_L`, `DOWN` | 스택 포인터를 늘리거나(자리 확보) 줄인다(자리 회수) |
| 적재/저장 | `LOD`, `LODS`, `LOD_A`, `LOD_C`, `STO` | 값 불러오기, 간접 적재, 배열 주소 적재, 상수 적재, 저장 |
| 산술 연산 | `ADD`, `SUB`, `MINU`, `MUL`, `DIV`, `MOD` | 덧셈·뺄셈·곱셈·나눗셈·나머지 |
| 논리 | `NOT` | 논리 부정 |
| 분기/점프 | `J`, `JMP`, `BZT`, `BEQ`, `BNE`, `BGT`, `BGE`, `BLT`, `BLE` | 무조건 점프, 0이면 점프, 비교 후 조건 점프 |
| 함수 | `CAL`, `RET` | 함수 호출, 함수 복귀 |
| 입출력 | `GET`, `GETC`, `PRF` | 정수 입력, 문자 입력, 출력(printf) |

`Interpreter.cpp`의 본체는 이 명령어들을 다음과 같이 `if/else if` 사슬로 하나씩 판별해 실행한다.

```cpp
if      (pCurCode->GetName() == "INT")  { sp += pCurCode->Getaddr(); at++; }
else if (pCurCode->GetName() == "LOD")  { /* 값 적재 */ }
else if (pCurCode->GetName() == "ADD")  { /* 덧셈 */ }
else if (pCurCode->GetName() == "JMP")  { /* 점프 */ }
// ...
```

즉 `Parser`는 "가상 명령어를 나열한 목록(pcode.txt)"을 만들고, `Interpreter`는 "그 가상 명령어를 이해하도록 미리 C++로 구현해 둔 가상 기계"로서 목록을 실행한다. 가상 명령어가 인터프리터를 만든 것이 아니라, 인터프리터가 가상 명령어를 해석·실행하는 관계임에 유의해야 한다.

## 12. 같은 이름을 어떻게 구분하는가: `(kind, scope)` 좌표와 스코프 스택

### 12.1 문제: 하나의 이름 `x`가 다섯 가지 의미를 가질 수 있다

소스 코드에서 이름 `x`는 지역 변수일 수도, 전역 변수일 수도, 함수명일 수도, 매개변수일 수도, 심지어 자기 자신을 호출하는 재귀 함수명일 수도 있다. 컴파일러 입장에서는 이 모든 경우가 **똑같은 문자열 "x"** 로 보인다. 따라서 이름만으로는 정체를 구분할 수 없다.

### 12.2 해결책 1: `kind`와 `scope` 두 좌표로 구분한다

`SymbolTable` 구조체는 이름 하나마다 두 개의 구분 좌표를 함께 저장한다.

```cpp
struct SymbolTable {
    std::string name;   // "x" — 문자열은 같을 수 있다
    int type = -1;      // 0=int, 1=char, 2=void
    int kind = -1;      // 0=변수, 1=함수, 2=매개변수, 3=배열   ← 무엇인가
    int scope;          // 1=전역, 2·3·4...=지역 블록마다 부여    ← 어디 소속인가
    ...
};
```

- `kind`는 "무엇인가"를 구분한다. 같은 `x`라도 `kind=0`이면 변수, `kind=1`이면 함수, `kind=2`이면 매개변수다.
- `scope`는 "어디 소속인가"를 구분한다. 전역은 1, 함수/블록에 들어갈 때마다 새 번호가 부여된다.

따라서 다음 코드에서 이름은 모두 `x`이지만 심볼 테이블에는 서로 다른 좌표로 등록된다.

```c
int x;                    // (kind=0 변수, scope=1 전역)
int foo(int x) {          // foo:(kind=1 함수, scope=1),  x:(kind=2 매개변수, scope=2)
    return x + 1;
}
int main() {
    int x;                // (kind=0 변수, scope=3 main 내부)
    x = foo(x);
    return x;
}
```

### 12.3 해결책 2: 사용할 때는 스코프 스택을 안쪽에서 바깥으로 탐색한다

이름을 "사용"하는 시점에는 여러 후보 중 어느 것인지 골라야 한다. `parseErrorC()`가 이 역할을 하며, 현재 위치에서 가장 안쪽 스코프부터 바깥으로 한 겹씩 거슬러 올라가며 탐색한다.

```cpp
std::stack<int> tempScopeStack = mScopeStack;   // 지금까지 들어온 스코프들의 사본
while (!tempScopeStack.empty()) {
    int currentScope = tempScopeStack.top();     // 가장 안쪽 스코프부터
    tempScopeStack.pop();
    SymbolTable* symbol = m_pSymbolTableMgr->findSymbol(name, currentScope);
    if (symbol != nullptr) { /* 찾음: 확정하고 break */ }
}
if (!isFound) { m_pErrorHandler->PushErrorList('c', mCurToken.lineNum); } // 끝까지 없으면 미정의 오류
```

이 "안쪽 우선" 탐색 덕분에 안쪽 스코프의 이름이 바깥 스코프의 같은 이름을 가리는 shadowing이 자연스럽게 구현된다. `main` 안에서 `x`를 쓰면 `scope=3`의 지역 변수가 먼저 잡히고, `scope=1`의 전역 `x`는 가려져 보이지 않는다.

### 12.4 재귀 함수명 처리: 몸통을 읽기 전에 이름을 먼저 등록한다

재귀가 성립하려면 함수 몸통 안에서 자기 이름을 찾을 수 있어야 한다. 이는 `ParseFuncDef()`가 **함수 몸통 `{ }`을 읽기 전에 함수 이름을 전역 스코프에 먼저 등록**하기 때문에 가능하다. 실제 처리 순서는 다음과 같다.

```cpp
void Parser::ParseFuncDef() {
    int kind = FUNC;                              // 451: 함수임을 표시
    std::string identname = mCurToken.word;       // 486: 함수 이름을 읽는다

    if (parseErrorB(identname, type, kind, 0, 1)) // 496: ★ 이름을 (함수, scope=1)로 먼저 등록 ★
    { valid_func = true; }

    mGlobalSymbolScope++;                         // 501: 함수 내부용 새 스코프 번호 발급
    mCurScope = mGlobalSymbolScope;
    mIsGlbScope = false;                          // 505: 이제 전역이 아니라 함수 내부

    ParseFuncFParam();                            // 511: 매개변수를 함수 내부 스코프에 등록
    parseErrorJ();                                // 518: ')' 확인

    ParseBlock();                                 // 523: ★ 이제서야 몸통을 읽는다 ★
}
```

핵심은 등록(496행)이 몸통 파싱(523행)보다 **먼저** 일어난다는 점이다. 그래서 523행에서 몸통 안의 `fact(n-1)` 같은 자기 호출을 만나 스코프를 탐색하면, 전역 스코프에서 이미 등록된 함수명을 찾을 수 있다. 만약 등록을 몸통 파싱 뒤에 했다면 자기 이름을 찾지 못해 미정의(`c`) 오류가 났을 것이고, 재귀가 성립하지 않았을 것이다.

또한 함수명은 **전역(scope=1)** 에 등록하고 매개변수는 **함수 내부 스코프**에 등록해야 하는데, 이 경계를 501행의 `mGlobalSymbolScope++`가 만든다. 이름 등록·스코프 전환·매개변수 등록의 순서를 정확히 맞추는 것이 재귀와 스코프 정합성의 전제 조건이다. 참고로 `main`은 자기 자신을 호출할 일이 없으므로 `ParseMainFuncDef()`에는 이런 선등록 로직이 없다.

## 13. 구현이 어려웠던 근본 이유: 단일 스캔에서 상태를 손으로 들고 다녀야 했다

7.5절에서 확인한 것처럼 최종 `Parser`에는 20개에 가까운 상태 변수가 있다. 이 상태 변수가 많다는 사실은 단순한 코드 스타일 문제가 아니라, single-pass(한 번 훑기) 구조가 강제한 결과다. 이 절은 그 어려움을 두 축(상태 깃발 관리, 스코프 번호 관리)으로 정리한다.

### 13.1 상태 깃발 관리: "기억을 손으로 들고 다니기"

한 번만 훑는 파서는 방금 지나온 문맥을 코드 구조로 되돌아볼 수 없다. 그래서 "지금이 전역인가 지역인가", "지금 함수 정의 중인가", "지금 for 문 안인가", "return을 이미 보았는가" 같은 문맥을 전부 상태 변수(깃발)에 기록해 들고 다녀야 한다.

| 깃발 | 기억하는 문맥 | 어긋났을 때의 증상 |
|---|---|---|
| `mIsGlbScope` | 전역인가 함수 내부인가 | 지역 변수를 전역으로 등록 |
| `mIsEqualScope` | 지금이 함수 최상위 블록인가 | 매개변수와 첫 지역 변수의 중복 판정이 틀어짐 |
| `mIsNeedReturn` | 이 함수가 반환값이 필요한가 | void 함수에 return 강요 또는 반대 |
| `mIsStmtReturn` | 방금 return을 보았는가 | "return 없음" 오판 |
| `mIsFor`, `mIsforincontinue` | for 문 내부인가 | break/continue의 점프 대상이 어긋남 |
| `mIsfuncDef` | 함수 정의 중인가 | 코드 생성 분기 규칙이 어긋남 |

가장 큰 난점은 각 깃발이 **켜고 끄는 짝**을 이룬다는 점이다. 예를 들어 `ParseFuncDef()`는 함수에 들어갈 때 `mIsGlbScope = false`로 껐다가(505행), 함수를 빠져나올 때 `mIsGlbScope = true`로 다시 켠다(527행). 만약 오류로 인해 중간에 다른 경로로 빠져 이 복원을 놓치면, 다음 함수를 처리할 때 여전히 `false`인 상태로 시작해 **전혀 다른 위치의 함수에서 전역 변수가 지역으로 등록되는** 문제가 생긴다.

이것이 이 구조에서 디버깅이 특히 어려웠던 이유다. 버그가 관측되는 위치와 원인이 발생한 위치가 수백 줄 떨어져 있어(action at a distance), 관측 지점만 보면 원인을 찾을 수 없다. 게다가 `mIsNeedReturn`(반환 필요)과 `mIsStmtReturn`(반환 봄)처럼 깃발끼리 짝으로만 의미를 갖는 경우가 있어, 하나의 리셋 타이밍이 어긋나면 앞 함수의 상태가 뒤 함수로 새는 연쇄 오류가 발생한다.

### 13.2 스코프 번호 관리: 세 변수의 수동 동기화

이 프로젝트의 심볼 테이블은 스코프 트리가 아니라 납작한 `std::vector<SymbolTable>` 하나이며, 소속은 오직 `scope` 번호로만 구분한다. 그래서 "지금 몇 번 스코프인가"를 프로그램이 손으로 계산해야 한다. 여기에는 세 개의 상태가 항상 정합적으로 유지되어야 한다.

- `mGlobalSymbolScope` — 스코프 번호 발급기 (계속 증가)
- `mCurScope` — 현재 스코프 번호
- `mScopeStack` — 지나온 스코프들(빠져나올 때 복귀용)

문제는 이 번호를 `ParseFuncDef()`와 `ParseBlock()`이 **함께** 조작한다는 점이다.

```text
ParseFuncDef: 501  mGlobalSymbolScope++;     // 함수용 번호 발급
              520  mGlobalSymbolScope--;      // 반납

ParseBlock:   613  mGlobalSymbolScope++;      // 블록용 번호 발급
              615  mScopeStack.push(mCurScope);
              647  mScopeStack.pop();          // 블록을 빠져나오며 반납
              650  mCurScope = mScopeStack.top();
```

함수 안에 블록이 있고 블록 안에 또 블록이 있으므로, 이 `++`/`--`와 `push`/`pop`의 짝이 하나라도 어긋나면 그 이후 모든 스코프 번호가 밀린다. 중첩이 깊을수록 짝 맞추기의 난이도가 올라간다.

또한 `ParseBlock()`에는 `mFuncStartScope == mCurScope` 비교가 세 번(618·639·654행) 등장하는데, 이는 **매개변수와 함수 몸통의 첫 지역 변수를 같은 스코프로 취급**하기 위한 장치다. 다음과 같은 중복을 잡아야 하기 때문이다.

```c
int foo(int n) {
    int n;      // 매개변수 n과 같은 스코프 → 중복 선언(b) 오류여야 한다
}
```

이 비교가 성립하면 `mIsEqualScope`가 켜지고, `parseErrorB()`가 매개변수 스코프까지 함께 조회해 중복을 검출한다. 결국 스코프 번호 계산(`mGlobalSymbolScope`/`mCurScope`) 또는 `mFuncStartScope` 세팅이 어긋나면, 멀쩡한 코드에 중복 오류가 나거나 진짜 중복을 놓치게 된다.

### 13.3 두 축을 관통하는 결론

상태 깃발 관리(13.1)와 스코프 번호 관리(13.2)는 뿌리가 같다. **"지금 나는 어느 스코프에 있고 어떤 문맥에 있는가"라는 하나의 진실을, 서로 떨어진 여러 변수에 손으로 복제해 유지해야 했다**는 점이다. single-pass 구조에서는 되돌아갈 수 없으므로 이 복제가 불가피했고, 그중 하나라도 어긋나면 전혀 다른 곳에서 버그가 관측되었다. 이것이 9장에서 서술한 "단일 파일 구조의 한계"를 코드 수준에서 뒷받침하는 근거이며, 왜 최종적으로 책임을 모듈로 분리하게 되었는지를 설명한다.

## 14. 최종 결론

1번부터 5번까지의 변화는 단순히 기능을 하나씩 추가한 과정이 아니다. 처음에는 테스트 파일과 어휘 분석에서 시작했지만, 구문 분석이 들어오면서 `i/j/k` 오류가 생겼고, 의미 분석이 들어오면서 오류 우선순위가 생겼으며, P-code 생성이 들어오면서 오류 복구 실패가 실행 결과까지 망가뜨리게 되었다.

특히 `i`, `j`, `k`는 컴파일러 구현에서 가장 까다로운 종류의 오류였다. 이유는 이 오류들이 “잘못된 토큰”이 아니라 “누락된 토큰”이기 때문이다. 입력에 존재하지 않는 토큰을 기준으로 오류를 판단해야 하므로, 현재 토큰을 소비할지 말지, 오류 줄 번호를 어디로 잡을지, 다음 문장으로 어떻게 복구할지가 모두 중요했다.

5단계는 P-code 생성과 인터프리터까지 구현했지만, 그만큼 파서가 너무 많은 책임을 가지게 되었다. `parseStmt()`, `ParseLVal()`, `ParseUnaryExp()`, `parsefor()` 같은 함수 안에서 문법 분석, 의미 검사, 오류 복구, 코드 생성이 동시에 수행되었다. 이 구조에서는 `i/j/k` 하나를 고치면 다른 기능이 깨질 가능성이 컸다.

따라서 최종적으로 `CMakeLists` 구조로 바꾼 것은 자연스러운 결정이었다. CMake 구조는 단순한 빌드 방식 변경이 아니라, 컴파일러의 복잡도를 감당하기 위한 구조적 전환이다. `Lexer`, `Parser`, `ErrorHandler`, `SymbolTableManager`, `Interpreter`를 분리함으로써 단일 파일에 몰려 있던 책임을 나누고, 특히 `i/j/k` 오류 처리, 배열 주소 계산, 함수 호출, 루프 라벨, P-code 실행처럼 서로 영향을 주는 부분을 더 명확하게 추적할 수 있게 되었다.

결론적으로 이 프로젝트의 핵심 변화는 다음 한 문장으로 정리할 수 있다.

> 1단계부터 5단계까지는 기능을 쌓아 올린 과정이었고, CMake 구조는 `i/j/k` 오류 복구, 심볼표, 배열/함수/루프 처리, P-code 생성과 실행이 얽히면서 생긴 복잡도를 감당하기 위한 최종 구조적 선택이었다.
