프로젝트

GXemul 환경에서 Lab0~Lab6의 7단계 커리큘럼을 따라 커널 부팅·메모리 관리·프로세스·시스템콜·IPC·파일시스템까지 OS의 핵심 구성요소를 단계적으로 직접 구현했습니다. 특히 TLB Fast Refill, Copy-on-Write 기반 fork(), 사용자 공간 FS 서버와 IPC를 통한 마이크로커널 파일시스템 구조를 구현하며 운영체제 핵심 메커니즘을 깊이 실습했습니다.

주요 개발 내용 (Lab0 – Lab6)

  • 커널 부팅 및 메모리 초기화 (Lab0–1): GXemul 시뮬레이터 환경에서 부트스트랩 코드 작성, 물리 메모리 레이아웃 설정 및 커널 엔트리 포인트 초기화.
  • 가상 메모리 체계 구축 (Lab2): 2단계 페이지 테이블 기반 가상 주소 공간 설계, TLB Miss 시 Fast Refill 핸들러를 어셈블리로 직접 작성해 TLB 관리 오버헤드 최소화.
  • 프로세스 스케줄링 (Lab3): PCB(Process Control Block) 설계, 라운드 로빈 스케줄러 구현, 컨텍스트 스위칭 시 레지스터 상태 저장·복원 로직 직접 작성.
  • 시스템콜 및 예외 처리 (Lab3–4): 시스템콜 인터페이스 설계, 사용자 모드·커널 모드 전환 시 Trapframe을 통한 레지스터 일괄 저장 및 복원 구현.
  • Copy-on-Write fork() 구현 (Lab4): 페이지 공유 후 쓰기 시 예외 기반 실제 복사가 일어나는 COW 메커니즘을 적용, 메모리 복사 비용을 지연 평가(Lazy Evaluation) 방식으로 최적화.
  • Pipe IPC 메커니즘 (Lab5): 공유 페이지 기반 파이프 구현, 파일 디스크립터 복제(dup) 및 참조 카운트(pageref) 관리 로직 설계.
  • 사용자 공간 파일시스템 (Lab6): 커널 내부가 아닌 독립된 FS 서버 프로세스와 IPC로 통신하는 마이크로커널 구조로 파일시스템 구현. 블록 캐시, 디렉토리 탐색, 파일 읽기·쓰기 시스템콜 연동까지 구성.

트러블슈팅

Pipe IPC 구현 중 매핑 순서에 따른 참조 수(pageref) 판정 오류 해결
Kernel / IPC
상황

dup() 및 close() 실행 시, FD와 Pipe 페이지의 매핑·해제 순서에 따라 pageref 값이 일시적으로 의도와 다르게 관측되는 레이스 컨디션이 발생했습니다.

대안 탐색

인터럽트 비활성화를 통한 임계 구간 보호를 검토했으나, 시스템 성능 저하와 교육용 OS의 설계 원칙을 고려해 제외했습니다. 대신 매핑 순서 재배치(Reordering)를 통해 항상 안전한 상태 불변식을 유지하는 방안을 선택했습니다.

해결

pageref(fd) ≤ pageref(pipe) 조건이 어떤 순간에도 깨지지 않도록 unmap·map 순서를 조정했습니다. IPC의 안정성을 확보했습니다.

pipe.c — Atomic-like Mapping Sequence
// 해제 순서 조정으로 불변식 유지
void pipe_close(int fdnum) {
  // [Fix] FD를 먼저 해제하여
  // pageref(fd) > pageref(pipe)
  //   찰나의 순간을 방지
  syscall_mem_unmap(0, fd_to_va(fdnum));
  syscall_mem_unmap(0, pipe_to_va(fdnum));
}
알게된 점

선점형 스케줄링 환경에서는 '완성된 결과'뿐만 아니라 '과정 중의 중간 상태'도 안전해야 함을 깨달았습니다.

초기 단일 파일 구조에서 Lexer, Parser, SymbolTable, ErrorHandler, Interpreter 모듈로 아키텍처를 분리하며 객체지향적 설계와 유지보수성을 개선했습니다.

주요 개발 내용

  • 어휘 분석기(Lexer) 구현: unordered_map으로 키워드 판별을 최적화하고, peek() 메커니즘으로 <=·==·&& 등 다중 문자 연산자와 이스케이프 시퀀스 포함 문자열 상수를 일관되게 토큰화.
  • 재귀 하향 파서(Recursive Descent Parser) 설계: CompUnit 선행 탐색, Stmt 내 LVal = Exp vs [Exp] 모호성 판별, 연산자 우선순위 기반 계층적 식(Expression) 파싱을 구현.
  • 스코프 기반 심볼 테이블: 스코프 ID + 스택 기반의 심볼 관리 구조로 스코프 체인 탐색을 지원하며, 변수 섀도잉(Shadowing), 함수 시그니처 불일치, 상수 재대입, 미선언 식별자 사용 등 의미 오류(Semantic Error)를 컴파일 타임에 검출.
  • 결함 허용(Fault-Tolerant) 에러 복구 시스템: 에러를 파싱 중단 사유가 아닌 '문맥 복귀 신호'로 재설계. 누락 토큰 오류는 직전 의미 단위의 기준 위치(mLastNonT)를 기록하도록 복구 로직을 정리해 연쇄 에러 출력을 줄이고 파싱을 중단하지 않고 후속 구문 분석을 지속.
  • P-Code 생성기 및 스택 머신 VM: 산술·논리 연산, 분기, 반복, 함수 호출/반환, 1차원 배열 인덱싱, I/O에 대한 자체 P-Code 명령어 셋을 설계하고, 이를 실행하는 스택 머신 인터프리터 구현.
  • 모듈화 및 아키텍처 리팩토링: 단일 대형 파일 구조에서 각 컴포넌트를 독립된 모듈로 분리해 디버깅 효율 및 유지보수성 향상.

트러블슈팅

이 컴파일러는 과제 명세에서 정의된 a~m 범주의 문법 및 의미 오류를 체계적으로 처리하도록 설계했습니다. 그중 가장 도전적이었던 과제는 세미콜론 누락(i) 발생 시 토큰 포인터 어긋남으로 인한 연쇄 오진을 방지하고, 파서를 정상 문맥으로 복귀시키는 구문 복구 로직의 구현이었습니다.

  • 구문 오류 복구: ;, ), ] 등의 토큰이 누락되어도 파싱을 중단하지 않고, 문맥을 복구하며 후속 구문 분석을 지속할 수 있도록 구현했습니다.
  • 의미 오류 진단: 중복 정의, 미선언 식별자, 함수 인자 개수/타입 불일치, 반환 규약 위반, 상수 재대입, printf 포맷 문자열과 인자 개수 불일치, 루프 밖 break/continue 사용 등을 컴파일 타임에 진단합니다.
  • 오류 출력 정책: 모든 에러를 줄 번호 기준으로 정렬한 뒤, 동일한 줄에서는 대표 오류 하나만 출력해 중복 보고를 줄였습니다.

아래 트러블슈팅은 그중 가장 설계 난도가 높았던 '구문 누락 복구' 문제를 시스템적으로 어떻게 해결했는지 다룹니다.

Fault-Tolerant 파서 구축 — 연쇄 파싱 에러 및 중복 오진 문제 해결
Compiler / Parser
상황

int a int b;처럼 세미콜론이 누락된 케이스를 처리하려고 에러 함수를 추가하면, 기존에 통과하던 정상 파싱까지 깨지는 문제가 반복됐습니다. 원인을 추적해보니 parseErrorI/J/K가 단순 검사 함수가 아니라 AdvanceToNextToken()으로 mCurToken/mCurpos를 직접 변경하는 함수였고, 호출 순서가 조금만 바뀌어도 후속 구문이 엉뚱한 토큰에서 시작했습니다.

대안 탐색

즉시 파싱 중단, 동기화 토큰(;, })까지 건너뛰는 panic-mode 복구, 그리고 새 검사를 기존 에러 함수 앞뒤에 삽입하는 방식을 비교했습니다. 하지만 커서를 소비하는 함수 앞에서 토큰을 한 번 더 이동시키면 ;가 이중 소비되거나 다음 선언의 첫 토큰을 건너뛰어 재귀 하향 파서 전체가 연쇄적으로 흔들렸습니다.

해결

먼저 에러 함수들을 토큰 소비형(parseErrorI/J/K), look-ahead형(parseErrorE), 심볼 등록형(parseErrorB)으로 분류했습니다. 이후 새 복구 로직은 현재 위치를 저장한 뒤 필요한 토큰만 미리 확인하고 원위치로 되돌리도록 정리했으며, 누락 토큰은 직전 의미 단위(mLastNonT) 기준으로 기록했습니다. 덕분에 에러 처리 추가가 다른 파싱 함수의 시작 위치를 망가뜨리는 문제를 줄였습니다.

Parser.cpp — Error Recovery
// parseErrorI/J/K는 검사 함수가 아니라 토큰 소비 함수
bool Parser::parseErrorI() {
  if (mCurToken.word != ";") {
    m_pErrorHandler->PushErrorList('i', mLastNonT);
    return true;
  }

  // 여기서 ';'를 소비하므로 호출 순서가 중요하다
  AdvanceToNextToken();
  return false;
}
알게된 점

이 경험을 통해 문제 해결 시 먼저 재현 가능한 최소 입력을 만들고, 상태를 바꾸는 함수와 읽기만 하는 함수를 구분해야 한다는 점을 배웠습니다. 에러 처리는 예외 출력보다 파서의 현재 위치와 문맥을 보존하는 설계가 더 중요했습니다.

상황

팀원 간 로컬 환경 설정(.env, AI 모델 경로) 차이로 인한 인프라 기동 실패가 발생했습니다. 또한, 개발자별로 상이한 API 응답 구조로 인해 프론트엔드에서 데이터 파싱 오류가 빈번하게 나타났습니다.

해결

README 기반 기동 프로세스를 확립하고, ResponseBodyAdvice를 활용해 모든 응답을 code/message/data 구조로 자동 래핑하는 아키텍처를 적용했습니다.

ResponseResultHandler.java
@RestControllerAdvice
public class ResponseResultHandler
    implements ResponseBodyAdvice<Object> {

  @Override
  public Object beforeBodyWrite(Object body, ...) {
    // 이미 공통 래퍼면 그대로 반환
    if (body instanceof ResultWrapper)
      return body;
    // 데이터를 규약에 맞춰 자동 래핑
    return ResultWrapper.success(body);
  }
}
알게된 점

협업 시 발생할 수 있는 휴먼 에러를 줄이기 위해서는 구두 약속보다 시스템(아키텍처)적으로 규약을 강제하는 설계가 팀 생산성에 기여한다는 점을 체감했습니다.

사용 기술

Spring Boot 3 Maven PostgreSQL Elasticsearch RedisMinIO Vue 3 TypeScript Docker Compose Vite

환자와 보호자를 연결하는 실시간 헬스케어 플랫폼입니다. 모바일(React Native) · 백엔드(Spring Boot) · AI 추론(FastAPI)으로 구성된 3-Tier 분리 구조를 설계하고 시스템 통합을 구현했습니다.

시스템 아키텍처

System Architecture — React Native · Spring Boot · FastAPI · PostgreSQL · AWS EC2 + Docker

주요 개발 내용

  • 3-Tier 분리형 아키텍처 구축: 비즈니스 로직(Spring Boot)과 고부하 AI 연산(FastAPI)의 책임을 물리적으로 분리하여 운영 안정성을 확보했습니다.
  • 심전도(ECG) 진단 모델 구현: PTB-XL 데이터셋을 활용한 CNN-CBAM-GRU 기반 추론 API를 구축하고 실시간 진단 기능을 연동했습니다.
  • 데이터 동기화 및 보안: JWT 인증 기반 401 만료 자동 로그아웃 흐름을 구현하고, AsyncStorage 기반 Cache-First 전략으로 클라이언트 응답성을 개선했습니다.

시스템 성능 최적화 및 평가 지표

  • 처리량(TPS) 평가: 20명 동시 접속 부하 테스트에서 주요 API 기준 TPS 56.23~66.41을 기록.
  • 실시간 AI 추론 속도: 12-lead ECG 데이터(10초 분량, 500Hz) 기준 AI 추론 속도는 평균 2,382.85ms, P50 2,303.27ms, P95 2,698.16ms.
  • 모바일 체감 로딩 개선: Cache-First 적용 후 Home 화면 첫 표시 평균 0.29ms, 네트워크 동기화 완료 평균 604.3ms.
  • 시스템 견고성 점검: Boundary Value Analysis 결과, 대부분의 비정상 입력은 서버 다운 없이 에러 응답으로 처리. NaN/Inf 포함 케이스에 대한 validation은 후속 보강 중.

ECG 분류 모델 성능

  • Macro F1: 74.52% · Macro AUC: 92.52% · HYP F1: 56.28% (comparison_results.csv 기준)
  • 모델 파라미터: 0.65M · 아키텍처: CNN-CBAM-GRU (Amplitude Feature Injection 36차원)
  • 손실 함수: 비대칭 손실(AsymmetricLoss) 및 클래스 불균형 보정(pos_weight) 기반 학습 전략 적용

① 증상 — ECG 분석 API 500

ECG 분석 요청(POST /api/ecg/analyze)이 간헐적으로 500을 반환했고, 백엔드 로그에는 FastAPI AI 서버로 보내는 /predict_window 요청이 Connection refused로 실패한 기록이 남았습니다.

② 추적 — 로그 범위 좁히기

docker logs carelink-backend로 백엔드의 외부 호출 실패를 확인한 뒤, docker ps -a와 docker logs carelink-ai로 AI 컨테이너가 종료됐는지 추적했습니다. 이어 journalctl -k, dmesg로 Ubuntu 커널 로그에서 OOM 여부를 확인했습니다.

③ 원인 — AI 컨테이너 종료

원인은 AI 컨테이너가 정상 기동하지 못한 것이었습니다. 배포 시 모델 파일 경로가 누락되면 FastAPI lifespan 단계에서 실패했고, 저사양 EC2에서는 이미지 빌드와 AI 모델 로딩이 겹치며 메모리 사용량이 급증해 OOM 가능성도 있었습니다.

④ 해결 — 모델 검증과 Pull-only 배포

모델 파일 배치 경로를 배포 체크리스트에 추가하고, 운영 EC2에서는 이미지를 직접 빌드하지 않도록 Pull-only 배포로 전환했습니다. 또한 mem_limit과 AI 컨테이너 profile 분리를 적용해 필요할 때만 추론 서비스를 실행하도록 구성했습니다.

sudo journalctl -k | grep -i "out of memory"
알게된 점

이 경험을 통해 문제 해결 우선순위를 증상 재현 → 애플리케이션 로그 → 컨테이너 상태 → OS 커널 로그 순서로 좁히는 습관을 만들었습니다. API 500도 코드만 보지 않고 프로세스 생존 여부와 인프라 자원까지 함께 확인해야 했습니다.
