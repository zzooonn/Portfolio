GXemul(MIPS R3000) 위에서 동작하는 교육용 OS를 구현한 개인 과제입니다. 커널의 메모리·예외·시스템콜 처리와 사용자 공간의 fork·IPC·파일 시스템·셸을 구현했습니다. 대표 사례는 파이프가 닫히지 않았는데 EOF로 판정한 동시성 오류입니다.

트러블슈팅

Pipe 거짓 EOF — dup/close 중간 상태를 닫힘으로 오판하는 문제
Kernel / IPC
상황

파이프가 닫혔는지는 커널에 묻지 않고 pageref(fd)와 pageref(pipe)를 비교해 판단합니다. 반대편이 살아 있으면 fd < pipe이고, 모두 닫히면 두 값이 같아져 EOF가 됩니다. 그런데 dup/close는 두 페이지를 각각 map·unmap하는 두 단계라서, testpiperace에서 그 사이에 타이머 인터럽트가 끼면 writer가 살아 있는데도 두 값이 순간적으로 같아져 reader가 EOF를 반환했습니다.

대안 탐색

처음에는 mutex로 중간 상태를 가리는 방법을 떠올렸습니다. 하지만 이 파이프는 사용자 공간 공유 페이지에서 동작해 공용 락이나 원자 연산이 제공되지 않았고, 락을 새로 만들면 락의 소유권과, 락을 잡은 프로세스가 죽었을 때의 복구라는 새 문제가 생겼습니다. 막아야 할 것은 모든 접근이 아니라 "writer가 살아 있는데 두 값이 같아 보이는 순간" 하나였습니다.

해결

중간 상태를 숨기는 대신 중간 상태가 틀린 의미를 갖지 않도록 순서를 바꿨습니다. dup은 pipe 페이지를 먼저 map하고, close는 fd 페이지를 먼저 unmap합니다. 그러면 어느 순간에 끊겨도 pageref(fd) < pageref(pipe)가 유지됩니다. 판정하는 쪽은 두 값을 읽는 사이에 스케줄 전환이 있었는지 env_runs로 확인하고, 있었다면 다시 읽습니다.

관련 코드 · 로그 보기
user/pipe.c — close 순서 · 닫힘 판정
/* ① close: fd를 먼저 내려 어느 순간에도 fd_ref < pipe_ref */
static int pipe_close(struct Fd *fd) {
  syscall_mem_unmap(0, fd);              /* fd 먼저 */
  syscall_mem_unmap(0, fd2data(fd));   /* pipe 나중 */
  return 0;
}

/* ② 판정: 두 값을 같은 실행 구간에서 읽었는지 확인 */
static int _pipe_is_closed(struct Fd *fd, struct Pipe *p) {
  int fd_ref, pipe_ref, runs;
  do {
    runs     = env->env_runs;
    fd_ref   = pageref(fd);
    pipe_ref = pageref(p);
  } while (runs != env->env_runs);  /* 도중에 스케줄되면 다시 읽기 */
  return fd_ref == pipe_ref;
}
알게된 점

다른 프로세스가 내 코드의 중간 상태를 볼 수 있다면 그 중간 상태도 설계 대상이었습니다. 이후 동시성 문제를 만나면 먼저 "다른 실행을 막아야 하는가, 아니면 중간 상태가 보여도 약속이 깨지지 않게 만들 수 있는가"를 묻게 됐습니다.

주요 개발 내용 (Lab0 – Lab6)

  • 프로세스와 스케줄링 (Lab3): Env(PCB) 할당, ELF 사용자 프로그램 적재, 타이머 인터럽트 기반 스케줄러 구현. 예외가 발생하면 Trapframe에 레지스터를 저장하고 복원해 사용자 모드로 돌아감.
  • 시스템콜 (Lab4): syscall 명령 → 예외 → 시스템콜 테이블 분기 → v0 반환 흐름 구현. 복귀할 때 EPC += 4로 같은 명령이 반복 실행되지 않게 처리.
  • Copy-on-Write fork (Lab4): 쓰기 가능한 페이지를 부모·자식 모두 PTE_COW로 공유하고, 쓰기가 일어나면 TLB Mod 예외에서 사용자 핸들러가 새 페이지를 복사. 핸들러가 COW 스택에 써서 같은 예외를 다시 일으키지 않도록 별도 예외 스택(UXSTACK)에서 실행.
  • 사용자 공간 파일 시스템 (Lab5): 커널 밖의 FS 서버 프로세스가 IPC로 요청을 처리하는 구조. 블록 캐시, 비트맵 기반 블록 할당, direct/indirect 블록, 경로 탐색 구현.
  • 셸과 파이프 (Lab6): spawn으로 실행 파일을 새 프로세스에 적재하고, 셸에서 리다이렉션(<, >)과 파이프라인(|) 구현. 파이프는 커널 버퍼가 아닌 사용자 공간 공유 페이지로 동작.

트러블슈팅

통과한 테스트, 깨진 입구 — 비로그인 검색 기록 조회 오류
백엔드 / 테스트
상황

검색 서비스에는 "로그인하지 않은 사용자의 검색 기록은 저장하지 않는다"는 규칙이 있었고, 서비스 단위 테스트도 통과했습니다. 그런데 로그인하지 않은 상태에서 검색 기록을 조회하면 요청이 NullPointerException으로 실패했습니다.

원인

요청을 가장 먼저 받는 컨트롤러가 서비스를 호출하기 전에 principal.uuid()로 로그인 정보부터 꺼내고 있었습니다. 규칙은 서비스 안에서 지켜지고 있었지만, 비로그인 요청은 그 규칙에 닿기도 전에 입구에서 멈췄습니다. 테스트는 서비스만 검증하고 있었습니다.

해결

로그인 정보가 없으면 검색 기록 조회는 빈 페이지를 바로 돌려주고, 검색어 분석은 사용자 식별값 없이 서비스로 넘기도록 고쳤습니다. 그리고 컨트롤러 단위 테스트를 새로 만들어 로그인한 경우와 하지 않은 경우를 모두 확인했습니다. 비로그인일 때 서비스의 기록 조회가 한 번도 호출되지 않는다는 점까지 검증했습니다.

알게된 점

NaN을 0으로 바꿨더니, 잘못된 파형에도 확률이 나왔다
Input validation / AI serving
문제

초기 전처리는 NaN을 0으로 치환했습니다. 요청은 처리됐지만, 센서 오류나 누락으로 생긴 값이 정상 신호의 진폭처럼 모델에 들어갔습니다. 추론이 성공했다는 사실만으로 입력의 의미까지 보장할 수 없었습니다.

판단과 변경

잘못된 값을 조용히 보정하는 대신 추론 전에 요청을 거부하도록 바꿨습니다. 빈 배열·비정형 배열·리드 수 불일치·숫자가 아닌 값·NaN/Inf·잘못된 샘플링 주파수를 검사합니다. 클라이언트가 보낸 진폭 특징 amp도 사용하지 않고 서버가 필터링 후 다시 계산합니다.

결과와 남은 한계

유효하지 않은 값이 모델의 확률로 바뀌는 경로를 막았습니다. 다만 내부 검증의 422 HTTPException이 넓은 예외 처리에 잡혀 500으로 반환될 수 있습니다. 추론 차단과 별개로, 클라이언트가 입력 오류를 구분할 수 있도록 상태 코드 전달을 고쳐야 합니다.

입력 검증과 전처리 흐름

행렬·숫자·유한값 검사 → 12리드 형태 통일 → 500Hz 리샘플링 → 5000샘플 길이 조정 → 대역 필터 → 진폭 특징 36차원 추출 → 리드별 정규화 → 추론

유효한 다른 샘플링 주파수는 500Hz로 변환합니다. 길이가 짧으면 앞쪽에 0을 채우고, 길면 뒤쪽 5000샘플을 사용합니다. 이는 NaN을 정상 관측값처럼 0으로 치환하는 처리와 구분했습니다.

모델 설계와 평가 기준

정규화 과정에서 진폭 정보를 잃지 않도록

CNN·CBAM·BiGRU로 파형과 시간 흐름을 처리하고, 필터링 후 정규화 전에 리드별 peak-to-peak·표준편차·RMS를 추출했습니다. 이 36차원 진폭 특징을 시계열 특징과 결합해 정규화로 사라질 수 있는 크기 정보를 별도로 전달했습니다.

평균 지표와 HYP 범주의 오류를 함께 비교

연구 비교 실험에서는 약 65만 파라미터 모델로 ResNet1D와 비슷한 전체 성능을 유지하면서 HYP 범주에서 더 나은 결과를 얻었습니다. 가중 샘플링을 제거했을 때 Macro F1·AUC는 높아졌지만 HYP 성능은 떨어졌습니다. 평균 지표와 범주별 오류를 함께 보고 손실 함수·샘플링 설정을 판단했습니다.

연구·서빙 구분: 비교 실험용 run_comparison.py와 서빙용 server.py·train_local.py는 같은 모델 이름을 쓰지만 CNN 깊이와 GRU 크기가 다릅니다. 연구 모델의 수치와 가중치를 서빙 모델에 그대로 적용할 수 없습니다. 전처리·임계값·모델 버전을 함께 관리하는 것이 후속 과제입니다.

Spring Boot ↔ PostgreSQL: 건강 기록·보호자 연결·알림 저장. ECG 추론 응답은 그대로 반환하며, 기록 저장은 별도의 건강 기록 API에서 수행합니다.

분리 이유: 인증·건강 기록을 처리하는 Java 백엔드와 모델 가중치·Python 의존성·전처리·추론 자원을 다루는 AI 서비스는 변경 주기가 달랐습니다. 앱은 Spring을 통해 AI에 접근하고, AI 실행 환경은 별도 컨테이너로 구성했습니다.

저메모리 서버에서 빌드와 실행을 나누기

한 EC2에서 PostgreSQL·JVM·PyTorch 실행과 이미지 빌드가 겹치면 메모리 사용이 몰렸습니다. FastAPI는 시작할 때 모델 가중치를 로드하므로, 모델 파일 누락이나 모델 구조 불일치도 기동 실패의 조건이었습니다.

이미지는 GitHub Actions에서 빌드해 GHCR에 저장하고, EC2에서는 pull 후 실행하도록 분리했습니다. 경량 Compose에는 PostgreSQL 256MB·백엔드 384MB·AI 512MB 제한을 두고, AI는 profiles: ["ai"]로 선택 실행하도록 구성했습니다. 모델 가중치는 이미지와 별도로 배치합니다.

메모리 제한만으로 OOM이 사라지는 것은 아닙니다. 경량 Compose에서 로컬 AI를 사용할 때는 AI_ECG_SERVER_URL과 양쪽 API 키를 별도로 맞춰야 합니다. 현재 구성이 자동으로 모든 배포 조건을 갖춘 것은 아닙니다.

인증·캐시·데모의 실제 동작

  • 인증: authFetch()는 401 응답 시 refresh token으로 갱신을 시도하고 원 요청을 재시도합니다. 갱신에 실패하면 세션을 지우고 초기 화면으로 돌아갑니다.
  • 캐시: 사용자명·프로필 이미지·보호자 목록을 먼저 읽고, 사용자 정보·건강 요약을 서버와 동기화합니다. 10초 이내 중복 요청을 막는 처리를 두었습니다.
  • 데모 범위: ECG 화면은 합성 신호와 서버 샘플을 사용합니다. 서버 샘플 파일이 없으면 생성한 데모 파형을 반환합니다. 건강 이상 알림은 DB에 저장하며 외부 push 발송은 로그 처리 수준입니다.

SysY의 Lexer·재귀 하향 Parser·심볼 테이블·P-Code 생성기·스택 머신 VM을 C++로 구현했습니다. 중복 정의와 함수 인자 불일치 등 의미 오류도 진단합니다. 대표 사례는 누락된 토큰 하나가 뒤의 정상 코드까지 오류로 만드는 문제입니다.

트러블슈팅

이 컴파일러는 과제 명세의 a~m 오류 범주를 처리해야 했습니다. 가장 오래 붙잡은 것은 ;·)·] 누락(i/j/k)이었습니다. 입력에 없는 토큰을 기준으로 판단해야 해서, 토큰을 하나 잘못 소비하면 뒤의 정상 코드까지 오류처럼 보였기 때문입니다.

) 하나 빠졌는데 오류가 여럿 — 오류를 기록에서 상태로 바꿔 파생 오류 제거
Compiler / Parser
상황

foo(a, b;처럼 )가 빠지면 핵심 오류는 j 하나입니다. 그런데 parseErrorJ()가 오류를 기록만 하고 끝나서, 호출자는 이를 모른 채 정상 호출처럼 인자 개수 검사(d)까지 수행해 파생 오류를 만들었습니다. 대입문을 판별하려고 앞 토큰을 읽고 index만큼 되돌아오는 코드도 한 번 어긋나면 b = 20;이 = 20;부터 읽혔습니다.

대안 탐색

처음에는 오류 함수 안에서 줄 번호 기준(이전 토큰/현재 토큰)만 바꿔 가며 테스트를 맞췄습니다. 테스트 하나를 통과시키면 다른 입력이 깨졌습니다. 문제는 오류 함수가 아니라 오류를 발견한 함수와 이후 처리를 맡은 함수가 오류 상태를 공유하지 않는 것이었습니다.

해결

parseErrorJ()의 반환형을 void에서 bool로 바꿔 누락 여부를 호출자에게 알리고, 호출부는 )가 있을 때만 인자 개수를 검사하도록 했습니다. 누락이면 현재 토큰을 소비하지 않아 다음 문장이 정상 위치에서 시작합니다. 이후에는 각 파싱 함수가 자기 문법 범위까지만 토큰을 소비한다는 규칙을 기준으로 코드를 정리했습니다.

관련 코드 · 로그 보기
Parser.cpp — parseErrorJ: void → bool
// Before: 기록만 하고 끝나 호출자는 ')' 누락을 모름
void parseErrorPrintfJ();

// After: 누락 여부를 반환하고, 누락이면 토큰을 소비하지 않음
bool Parser::parseErrorJ() {
  if (mCurToken.word != ")") {
    m_pErrorHandler->PushErrorList('j', mLastNonT);
    return true;
  }
  AdvanceToNextToken();
  return false;
}

// 호출부: ')'가 있을 때만 인자 개수(d) 검사
if (!parseErrorJ()) {
  if (mFuncparse.back().expectedcnt != mFuncparse.back().paramcnt)
    parseErrorD(mLastFuncLine);
}
알게된 점

오류는 사용자에게 보여줄 기록에서 끝나지 않고, 이후 어떤 검사를 믿을 수 있는지 결정하는 상태여야 했습니다. 괄호 하나가 빠졌는데 오류가 열 개 나온다면, 아홉 개는 컴파일러가 스스로 만든 오류일 수 있습니다.

상세 구현 · 구조 · 측정

주요 개발 내용

  • 어휘 분석기(Lexer) 구현: unordered_map으로 키워드 판별을 최적화하고, peek() 메커니즘으로 <=·==·&& 등 다중 문자 연산자와 이스케이프 시퀀스 포함 문자열 상수를 일관되게 토큰화.
  • 재귀 하향 파서(Recursive Descent Parser) 설계: CompUnit 선행 탐색, Stmt 내 LVal = Exp vs [Exp] 모호성 판별, 연산자 우선순위 기반 계층적 식(Expression) 파싱을 구현.
  • 스코프 기반 심볼 테이블: 심볼마다 kind(변수·함수·매개변수·배열)와 scope 번호를 붙여 같은 이름을 구분하고, 가장 안쪽 스코프부터 바깥으로 탐색해 섀도잉을 처리. 함수 이름을 몸통보다 먼저 등록해 재귀 호출이 미정의 오류가 되지 않게 함.
  • 누락 토큰 오류 복구: ;·)·] 누락(i/j/k)은 "틀린 토큰"이 아니라 "없는 토큰"이므로, 눈앞의 정상 토큰을 소비하지 않고 오류만 기록한 뒤 분석을 계속. 오류 줄 번호 기준을 오류마다 따로 두지 않고 mLastNonT 하나로 통일.
  • P-Code 생성기 및 스택 머신 VM: 산술·논리 연산, 분기, 반복, 함수 호출/반환, 1차원 배열 인덱싱, I/O에 대한 자체 P-Code 명령어 셋을 설계하고, 이를 실행하는 스택 머신 인터프리터 구현.
  • 모듈 분리와 CMake: 하나의 대형 파일에 섞여 있던 Lexer·Parser·ErrorHandler·SymbolTableManager·Interpreter를 파일 단위로 나누고 CMake로 빌드. 문제가 생겼을 때 어디부터 봐야 하는지 알 수 있게 됨.

STM32(Cortex-M0+)에서 버튼을 누르는 동안 LED가 200ms 간격으로 토글되도록 코드를 고치며 Polling과 Interrupt를 비교했습니다. OS에서는 예외 벡터와 핸들러만 봤다면, 여기서는 버튼 → EXTI → NVIC → ISR 경로를 레퍼런스 매뉴얼로 따라가고, 디바운싱처럼 시뮬레이터에는 없던 물리 입력의 문제를 다뤘습니다.
