01

SysY 언어 컴파일러 프론트엔드 & VM

2024.10 – 2025.01 · 1인 개발
C++17/CMake · Lexer/Parser/Symbol Table/P-Code VM · Fault-Tolerant 파서

SysY 언어의 Lexer, 재귀 하향 Parser, Symbol Table, P-Code VM 전 과정을 C++17과 CMake로 구현하고, 구문 오류가 발생해도 파싱을 중단하지 않는 결함 허용 구조를 설계했습니다.

구현
  • CompUnit 선행 탐색, Stmt 내 대입문/표현식 모호성 판별, 연산자 우선순위 기반 식 파싱을 직접 구현했습니다.
  • 스코프 체인 기반 심볼 테이블로 중복 선언, 미정의 식별자, 상수 재대입, 함수 시그니처 불일치를 컴파일 타임에 진단했습니다.
  • 산술·논리 연산, 분기, 반복, 함수 호출/반환, 배열 인덱싱, I/O를 위한 자체 P-Code 명령어와 스택 머신 VM을 구현했습니다.
문제

세미콜론 누락 에러 복구 시 토큰 포인터가 과도하게 이동해 정상 구문까지 연쇄적으로 오류로 판정하는 문제가 발생했습니다.

해결

에러를 파싱 중단 사유가 아닌 문맥 복귀 신호로 재정의하고, 직전 유효 토큰 위치인 mLastNonT를 기록해 파서를 중단하지 않고 정상 흐름으로 복구하도록 개선했습니다.

연결점

DBMS 엔진의 SQL 파서, 의미 검증, 실행 계획/중간 표현을 학습하기 위한 기반으로 연결됩니다. 입력을 해석하고 내부 표현으로 바꾸는 시스템을 직접 설계했다는 점을 강조할 수 있습니다.

MIPS 마이크로커널 운영체제

2024.03 – 2024.07 · 1인 개발
C 기반 OS Kernel · 가상 메모리/프로세스/IPC/파일 시스템 · Lock-free IPC 문제 해결

MIPS 아키텍처 위에서 부팅, 가상 메모리, 프로세스, 시스템콜, IPC, 파일 시스템까지 OS 핵심 구성요소를 구현하며 DBMS 엔진 개발에 필요한 시스템 내부 동작 감각을 쌓았습니다.

구현
  • 2단계 페이지 테이블과 TLB Fast Refill 핸들러를 어셈블리로 최적화하고, Copy-on-Write 기반 fork()를 구현해 프로세스 생성 비용을 낮췄습니다.
  • 사용자 공간 FS 서버와 공유 페이지 기반 Pipe IPC를 구현해 커널과 파일 시스템을 분리하고, 블록 캐시·디렉토리 탐색·파일 읽기/쓰기 흐름을 구성했습니다.
문제

Pipe IPC 구현 중 스케줄링 타이밍에 따라 열린 파이프를 닫힌 것으로 오인하는 동시성 문제가 발생했습니다. 단순히 인터럽트를 막는 방식보다 근본 원인인 매핑 순서 의존성을 분석했습니다.

해결

close()와 dup() 호출 시 페이지 map/unmap 순서를 재배치해 pageref(fd) ≤ pageref(pipe) 불변식이 항상 유지되도록 설계했습니다. 락을 추가하지 않고 실행 순서 재배치로 안정성을 확보했습니다.

연결점

DBMS 엔진이 의존하는 메모리, 프로세스, 파일 I/O, 동시성 제어를 직접 구현한 경험입니다. 엔진 버그 수정 시 상태와 참조 관계를 끝까지 추적하는 태도로 연결됩니다.

학술 성과 공유 플랫폼 — Java DB 백엔드

2025.03 – 2025.08 · 백엔드 전담
Java 21/Spring Boot · PostgreSQL/Elasticsearch/Redis/MinIO 통합 · 기술문서/RFC · API 오류 0건 수렴

Vue 3 프론트와 Spring Boot 백엔드, PostgreSQL, Elasticsearch, Redis, MinIO를 연결해 검색·상세 조회·분석·외부 API 연동이 가능한 데이터 중심 플랫폼을 구축했습니다.

구현
  • Spring Boot 3(Java 21) 환경에서 PostgreSQL, Elasticsearch, Redis, MinIO를 연동하고 데이터 조회·검색·파일 저장 흐름을 분리했습니다.
  • 검색 요구에 맞춰 RDBMS와 Elasticsearch를 비교 운용하고, 10만 건 더미 데이터 기준 응답 속도를 측정해 기술 선택 근거를 만들었습니다.
  • docs/와 RFC를 중심으로 요구사항, 아키텍처, 데이터 설계, API 인터페이스를 문서화했습니다.
문제

팀원마다 API 응답 구조가 달라 프론트엔드 파싱 오류가 반복됐고, 로컬 환경 설정 차이로 인프라 기동 실패가 발생했습니다. 문서 합의만으로는 재발을 막기 어려웠습니다.

해결

Spring의 ResponseBodyAdvice로 컨트롤러 반환값을 항상 {code, message, data} 구조로 래핑하고, Docker Compose와 README/RFC로 실행 조건을 표준화해 API 파싱 오류를 0건으로 수렴시켰습니다.

연결점

DBMS 사용 경험을 넘어 저장·검색 계층을 어떻게 분리하고, 기술문서를 통해 팀의 실행 환경을 어떻게 통일했는지 보여 주는 프로젝트입니다.

CareLink — Java 서비스와 배포 안정화

2025.10 – 2026.03 · 1인 개발 / 졸업논문
Spring Boot 3/Java 21 · PostgreSQL · FastAPI 분리 · AWS EC2/Docker · TPS 66 · OOM 대응

Spring Boot 백엔드와 FastAPI 추론 서버, PostgreSQL을 분리한 3-Tier 구조를 설계하고 AWS EC2와 Docker 기반으로 배포해 서비스 안정성과 자원 제약을 함께 검증했습니다.

구현
  • Java/Spring Boot 비즈니스 로직과 Python/FastAPI AI 추론 서버를 분리해 장애 범위와 자원 사용량을 독립적으로 관리했습니다.
  • JWT 인증, 자동 로그아웃, Cache-First 조회 전략을 적용하고 20명 동시 접속 기준 주요 API TPS 56.23~66.41을 측정했습니다.
문제

AI 컨테이너와 백엔드를 동시에 구동하면 1GB RAM EC2에서 OOM이 반복됐습니다. 서버에서 직접 이미지를 빌드하는 방식은 배포 중 서비스 안정성을 떨어뜨렸습니다.

해결

로컬과 CI에서 이미지를 빌드해 레지스트리에 push하고, 서버는 Pull-only로 운영하도록 전환했습니다. Docker mem_limit과 profile로 컨테이너별 자원을 격리했습니다.

연결점

패키지 소프트웨어 개발에서 중요한 재현성, 배포 안정성, 자원 제약, 성능 수치 확인 습관을 보여 줍니다. 엔진 개발 후 테스트와 운영 품질까지 의식하는 근거로 활용할 수 있습니다.
