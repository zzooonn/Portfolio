🎯 목표

MIPS 아키텍처 위에서 부팅 → 가상 메모리 → 프로세스 → 시스템콜 → IPC → 파일 시스템까지 OS 핵심 구성요소를 직접 구현하여, 커널 레벨 동시성 제어 원리를 체득합니다.

  • 가상 메모리 및 프로세스: 2단계 페이지 테이블과 TLB Fast Refill 핸들러를 어셈블리로 최적화하고, Copy-on-Write(CoW) 기반 fork()를 구현해 프로세스 생성 시 메모리 오버헤드를 최소화했습니다.
  • 마이크로커널 구조: 사용자 공간에서 동작하는 FS 서버 프로세스를 구축하고, 공유 페이지 기반 Pipe IPC 메커니즘을 구현하여 커널과 파일 시스템을 물리적으로 분리했습니다.
🚨 트러블슈팅: 락(Lock) 없는 IPC 레이스 컨디션 해결

Pipe IPC 구현 중 스케줄링 타이밍에 따라 열린 파이프를 닫힌 것으로 오인하는 동시성 문제가 발생했습니다. 성능 저하를 유발하는 인터럽트 비활성화 대신, 근본 원인인 '매핑 순서 의존성'을 분석했습니다. close()와 dup() 호출 시 페이지 map/unmap 순서를 재배치하여 pageref(fd) ≤ pageref(pipe) 불변식이 항상 유지되도록 설계, 락(Lock) 없이 안정적인 동시성 제어를 구현했습니다.

👤 본인 기여

부팅부터 셸까지 전 단계를 1인 단독 설계 및 구현했습니다. 특히 IPC 레이스 컨디션은 하드웨어 제어 없이 코드 실행 순서 재배치만으로 불변식을 강제하는 구조적 해결책을 직접 도출했습니다.

💡 배운 점

선점형 스케줄링 환경에서는 완성된 결과뿐 아니라 '실행 중간 상태'도 항상 안전해야 한다는 것을 체득했습니다. 락 같은 외부 도구 없이 코드 순서만으로 불변식을 보장하는 설계가 성능과 안전성을 동시에 달성하는 방법임을 배웠습니다.

02 SysY 언어 컴파일러 프론트엔드 & VM
2024.10 – 2025.01  1인 개발 (Compiler Engineer)

🎯 목표

SysY 언어의 Lexer → 재귀 하향 Parser → Symbol Table → P-Code VM 전 과정을 C++17로 구현하고, 구문 오류가 발생해도 파싱을 중단하지 않는 결함 허용(Fault-Tolerant) 파서를 설계합니다.

  • 구문 및 의미 분석: 모호성을 해결하는 재귀 하향 파서를 설계하고, 스코프 체인을 지원하는 심볼 테이블을 구축하여 함수 시그니처 불일치중복 선언 등 의미 오류를 컴파일 타임에 진단했습니다.
  • 아키텍처 모듈화: 단일 파일 구조에서 LexerParserSymbolTableErrorHandlerInterpreter 5개 독립 모듈로 리팩토링하여 에러 복구 로직 수정 시 파싱 전체가 흔들리는 문제를 해결했습니다.
🚨 트러블슈팅: Fault-Tolerant 파서로 연쇄 오진 해결

세미콜론(;) 누락 에러 복구 시, 토큰 포인터가 과도하게 이동해 정상 구문까지 연쇄적으로 오류 오진하는 문제가 발생했습니다. 에러를 '파싱 중단 사유'가 아닌 '문맥 복귀 신호'로 재설계하고, 직전 유효 토큰 위치(mLastNonT)를 기록하여 파서를 중단하지 않고 정상 흐름으로 복구시키는 결함 허용 파서를 완성했습니다.

04 CareLink — 실시간 노인 심전도(ECG) 진단 플랫폼

🎯 목표

환자,보호자 연결 모바일 앱과 실시간 ECG AI 진단 기능을 단일 서버가 아닌 프론트(React Native),백엔드(Spring Boot),AI 추론(FastAPI) 3-Tier로 분리하여, 제한된 AWS 인프라에서도 안정적으로 운영 가능한 헬스케어 플랫폼을 구축합니다.

  • AI 모델 고도화: PTB-XL 데이터셋 기반으로 12-lead 진폭 특성(36차원)을 직접 설계해 분류기에 주입한 CNN-CBAM-GRU 모델을 구축했습니다. HYP 클래스 F1이 56%에 머무는 문제를 SMOTE 증강 시도 후 Focal Loss 손실 함수로 전환해 Macro AUC 92.52%를 달성했습니다.
  • 3-Tier 분리 구조: 비즈니스 로직(Spring Boot)과 고부하 AI 연산(FastAPI)을 물리적으로 분리하고, JWT 인증 기반 자동 로그아웃 및 Cache-First 전략으로 프론트의 응답성을 개선했습니다.
🚨 트러블슈팅: 저사양 EC2 OOM 셧다운 → Pull-only 배포 전략으로 해결

AI 컨테이너와 백엔드를 동시 구동하면 1GB RAM EC2에서 OOM이 반복됐습니다. JVM 힙 튜닝을 시도했으나 절대적 메모리 부족은 코드 최적화만으로 해결할 수 없었습니다. 로컬/CI에서 이미지를 빌드 후 레지스트리에 push하고 서버는 Pull-only로만 운영하는 전략으로 전환했으며, Docker mem_limit으로 컨테이너별 자원을 격리하고 AI 컨테이너는 profile로 분리해 필요 시에만 기동하도록 개선했습니다.
