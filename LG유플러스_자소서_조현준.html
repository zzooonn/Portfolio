GPU 기술 TF가 풀려는 문제를 채용공고에서 역으로 그렸습니다

"AI 추론 워크로드 분석", "GPU 활용 SW 개발", "시스템 성능 분석"이라는 키워드에서 팀의 핵심 과제를 역추론했습니다. 모델·배포·하드웨어 어느 계층에서 병목이 생기는지를 코드 단위로 특정해 GPU 자원을 효율적으로 쓰는 일이 본질이라고 판단했습니다. 저는 CareLink에서 PyTorch 추론 서버를 FastAPI로 감싸 t2.micro에 배포한 뒤, 추론 평균 2,382ms / P95 2,698ms를 실측해 Spring Boot API 응답(약 320ms)과 물리적으로 분리해 병목을 모델 추론 단계로 특정한 경험이 있습니다. 같은 추적 방식을, 단일 추론 지연을 넘어 다수의 GPU 워커가 도는 추론 서빙 환경으로 한 단계 확장하는 자리가 GPU 기술 TF라고 이해했습니다.

솔직한 자기 인식 · GPU·CUDA 경험은 공백입니다
없는 경험을 꾸미는 대신, 지금까지 무엇으로 그 자리를 메워왔는지 말씀드리고 싶습니다

저는 아직 GPU 커널을 작성해 본 적도, CUDA로 행렬 연산을 가속해 본 적도 없습니다. 우대사항으로 명시된 영역이고 인턴 기간 중 학습 기회가 주어진다는 공고 내용을 보고 지원하지만, 자소서에서 이 부분을 부풀려 적지는 않겠습니다. 대신 저는 MIPS 어셈블리로 TLB Miss Fast Refill 핸들러를 직접 작성하고, COW fork에서 페이지 권한 비트와 매핑 순서를 한 줄씩 추적해 본 사람입니다. 메모리·캐시·병렬성·예외 처리라는 GPU 컴퓨팅의 토대를 시스템 SW 레벨에서 다져 왔기 때문에, GPU 아키텍처와 CUDA 프로그래밍 모델은 새 언어가 아니라 기존 사고의 확장으로 받아들일 수 있다고 판단합니다. 인턴 기간을 GPU라는 새 컴퓨팅 모델로 시스템 역량을 옮기는 자리로 쓰고 싶습니다.

핵심 역량 01 · CareLink — AI 추론 지연 실측 → 병목 단계 분리 → 경로 재설계
"왜 느린가"를 P95 단위로 측정하고 추론 단계로 좁혀, 시스템 경로를 다시 그렸습니다

ECG 진단 플랫폼 CareLink에서 사용자 체감 응답이 일관되게 느린 문제가 있었습니다. "AI 추론이 느리다"는 가설을 검증하기 위해 Spring Boot API 응답과 FastAPI 추론 응답을 동일 부하 시나리오에서 분리 측정했고, 평균 2,382.85ms / P50 2,303ms / P95 2,698.16ms라는 수치를 얻었습니다. 일반 API는 평균 약 320ms로 정상이었기 때문에 병목은 모델 추론 단계 단일 지점이라고 특정할 수 있었습니다. 이 결과를 근거로 AI 경로와 일반 경로를 물리적으로 분리하고, 일반 API에는 AsyncStorage Cache-First를 도입해 Home 첫 표시 평균 0.29ms를 달성했습니다. 운영 중에는 docker logs → docker ps -a → journalctl -k → dmesg 순서로 OOM 가능성까지 좁혀 추론 컨테이너를 profile 분리하고 mem_limit를 명시했습니다. 동시 부하 20명 기준 TPS 66.41을 유지했습니다. GPU 추론 환경에서도 같은 사고 방식 — 어느 워커, 어느 커널, 어느 메모리 전송 단계에서 시간이 새는지를 수치로 분리해 좁히는 일 — 이 그대로 작동한다고 봅니다.

핵심 역량 02 · SysY 컴파일러 · MIPS OS — 표면 증상이 아닌 근본 구조까지
"수정했더니 통과하던 케이스가 깨졌다" — 그때 비로소 진짜 원인을 만났습니다

SysY 컴파일러에서 세미콜론 누락 케이스를 처리하기 위해 에러 함수를 추가했더니, 기존에 정상 통과하던 파싱이 깨지는 회귀가 발생했습니다. 증상은 새 코드에서 났지만, 원인은 따로 있었습니다. parseErrorI/J/K가 단순 검사 함수가 아니라 내부적으로 mCurToken·mCurpos를 직접 변경하는 함수였고, 호출 순서가 조금만 바뀌어도 다음 선언 첫 토큰이 통째로 스킵되는 구조였습니다. 즉시 중단·panic-mode·삽입 위치 변경 등 표면적 시도는 모두 실패했고, 결국 에러 함수를 "토큰 소비형 / look-ahead형 / 심볼 등록형" 3종으로 분리하고 새 복구 로직은 현재 위치 저장 → look-ahead → 원위치 복귀 구조로 다시 짰습니다. MIPS OS Lab 4의 Pipe IPC에서도 같은 패턴이 있었습니다. dup()/close() 직후 일시적으로 pageref(fd) > pageref(pipe)가 관측되는 레이스 컨디션을, 락 추가 대신 unmap·map 순서를 바꿔 불변식이 깨지지 않게 재설계했습니다. "선점형 환경에서는 완성된 결과뿐 아니라 중간 상태도 안전해야 한다" — GPU 워크로드의 비결정적 타이밍과 메모리 일관성 문제에 그대로 통하는 사고입니다.

왜 LG U+ GPU 기술 TF인가 · 일하는 방식과 마지막 선언
새 기술이 들어오는 자리에서, 시스템 레벨로 내려가 책임지겠습니다

LG U+는 통신사 인프라 위에 자체 AI 추론 서비스를 올리는 단계에 들어와 있고, GPU 기술 TF는 그 추론 워크로드를 시스템 레벨에서 책임지는 자리라고 이해했습니다. 새 기술이 들어오는 자리에서는 증상에 대한 임시 수정이 가장 위험하고, 원인 레이어를 끝까지 좁히는 사람이 가장 필요합니다. 저는 그 일을 학부 내내 해 왔고, 인턴 기간에는 부족한 GPU·CUDA 학습을 빠르게 메우면서 추론 지연·메모리 점유·동시성 이슈를 측정하고 좁히는 작업에 기여하겠습니다. 9년의 베이징 생활과 TSC Level 6은, 중국 발 GPU·AI 인프라 문헌과 오픈소스 이슈를 1차 소스에서 직접 읽고 팀에 옮길 때 부수적인 강점이 될 것입니다. 이 인턴십이 끝날 때 "GPU 추론 서빙의 한 단면은 이 친구에게 맡겨도 된다"는 평가를 받는 것이 목표입니다.
